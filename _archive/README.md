# 归档：实时语音合成（已停用）

这里有约 **8000 行**代码，是 PetPC 曾经用来**实时合成语音**的整套实现。
它已经**不再参与构建**，保留下来只作参考。

## 为什么停用

用户的判断是"一是太慢，二是效果不稳定"，而实测数据完全支持：

| 问题 | 实测 |
|---|---|
| **太慢** | 在线合成 54 字要 **11 秒**（冷启动 36.7 秒）；本地 RTF 0.894 |
| **太重** | 本地模型常驻 **3.3 GB** 内存（一个桌宠） |
| **不稳定** | 上游服务自己标注「结果有随机性」 |
| **复杂度失控** | 为修"句子被切断"一个问题，改了 **4 轮**，其中一次方向是错的 |

而桌宠真正需要的朗读只有**两类固定通知**：番茄钟结束、待办提醒。
台词固定 → 可以**离线合成一次、永久复用** → 零延迟、零内存、零依赖。

现在的实现见 `internal/voice`：5 个内嵌音频、569 KB、即时播放。

## 如果将来要重启这条路

值得先读的几件事，都是踩过的坑：

1. **切句只能切在句末标点**。在逗号处切会让每个片段都是**残句**，
   TTS 给不出句末语调，拼起来就是"每句都被掐断"。
   证据在 `tts-probe/test_fragment_theory.py`：同一段话按逗号切 5 段 vs 按整句切 2 段，
   用户**一次听辨**就定案。

2. **"音频秒数"不是可信的截断指标**。三次测量中，同一指标给出过**相反方向**的结果
   （`ws_size_sweep.py`、`ws_noise.py`）。要判断截断应做**语音识别回读**，而不是比时长。

3. **在线桥接的三个协议坑**（`tools/tts-online/bridge.py` 里有完整注释）：
   - Gradio 3.7 用 **WebSocket 队列**，握手是三步，要**发两次**同样的任务
   - 参数顺序是**组件 ID**（`[6,7,13,15,16,17]`）而非数组位置；顺序错会"成功但输出为空"
   - 角色名**必须精确**；错了**不报错，只返回空音频**
   - 单次上限 100 字，超了返回 `输入文字过长` 且**完全不出声**

4. **播放必须走文件**，不能用 `SND_MEMORY`：winmm 的异步播放要求调用方缓冲区存活，
   而 Go 的 GC 不知道这件事，一次回收就会静音或崩溃（约百分之一的概率）。
   现在的 `internal/voice` 也遵循这一条。

## 恢复方式

1. 从 `_archive/tts-realtime/` 把文件移回原位
2. 恢复 `internal/store/tts.go` 里的 19 个配置字段与 `NormaliseTTS`
3. 恢复 `app.go` 里的 `Speech SpeechView` 状态字段与 `initSpeech`
4. 恢复 `app_llm.go` 里 `runChat` 的朗读接线（`startSpeech`/`holdText`/`finishSpeech`）
5. 恢复前端设置区与 `.dev/check-frontend.cjs` 的对应检查段

> 第 5 步要注意：**检查脚本当初把错误行为当成了正确行为**。
> 它曾断言"到达上限时退回逗号切分"是**必须**的 —— 而那正是"断开"的病因。
> 恢复时请先想清楚要断在哪里，再写断言。
