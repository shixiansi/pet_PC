# 在线语音（原神音色，不占本机）

`bridge.py` 在本机发布一个 **和 GPT-SoVITS 完全一样**的 `/tts` 接口，
背后用公共 HuggingFace Space 合成。因此在 PetPC 里切换语音来源**不需要改任何客户端代码**。

## 为什么做成"桥接"而不是直接在 Go 里实现在线协议

| 理由 | 说明 |
|---|---|
| **复用已有的一切** | 切句、缓存、打断、播放流水线、错误分类全部照用——在线模式只是"WAV 字节的另一个来源" |
| **协议差异被隔离** | 上游是 Gradio 3.7 的 **WebSocket 队列**（三步握手）。在 Go 里实现意味着自带 WebSocket 客户端 + 手写协议，换不来任何好处 |
| **上游挂了只坏一个文件** | Space 下线时只需改/换 `bridge.py`；把地址切回本地 `api_v2.py` 就恢复，PetPC 本身不受影响 |

## 用法

```powershell
# 1. 启动桥接（首次会自动确认 websockets 依赖）
powershell -ExecutionPolicy Bypass -File tools\tts-online\start-bridge.ps1 -Speaker 可莉

# 2. 看看有哪些音色（804 个，其中原神 97 个）
powershell -ExecutionPolicy Bypass -File tools\tts-online\start-bridge.ps1 -ListVoices

# 3. 在 PetPC 里：设置 → 语音朗读 → 语音来源 =「在线」，地址 http://127.0.0.1:9881
```

桥接默认监听 **9881**，本地 GPT-SoVITS 用 **9880**，**两个可以同时开着**，
在面板里切换即可，不需要重启任何一个。

## 上游的硬限制（都已实测，桥接已处理）

| 限制 | 表现 | 桥接的处理 |
|---|---|---|
| **单次最多 100 字** | 110 字时返回 `输入文字过长！110>100`，**完全不出声** | 超过就返回明确错误，**绝不静默截断**（静默截断会让桌宠念半句话） |
| **角色名错了不报错** | 任务"完成"但返回空音频 | 返回可操作提示，并列出音色总数与最接近的名字 |
| **排队/休眠** | 免费 Space 会排队，冷启动慢 | 3 次重试 + 内容缓存（重复台词直接命中，实测 7ms） |

> **100 字上限正好说明切句是必需的**。PetPC 默认按 ~20 字切句，天然满足；
> 如果关掉切句直接发整段回复，就会撞上这个限制。

## 实测数据

| 项 | 结果 |
|---|---|
| 可用音色 | 804（原神中文 97） |
| 合成耗时 | 0.9 ~ 7.6 秒（随句子长度） |
| 缓存命中 | **7 ms** |
| 本机占用 | 桥接进程约 **30 MB**（对比本地 GPT-SoVITS 的 **3.3 GB**） |

## 参数

```
--host       上游 Space 域名（默认 zomehwh-vits-uma-genshin-honkai.hf.space）
--port       监听端口（默认 9881）
--speaker    初始音色
--cache-dir  缓存目录（默认 ~/.petpc-online-tts；传空串关闭）
--cache-mb   缓存上限（默认 300）
--token      可选共享密钥；PetPC 侧填在 API Key 里
--list-voices 列出音色后退出
```

## 排错

| 现象 | 原因 |
|---|---|
| 面板显示"连不上语音服务" | 桥接没启动，或地址不是 9881 |
| 下拉显示"连不上在线服务" | 桥接在跑但拉不到音色列表（上游不可达）；看桥接窗口的日志 |
| 某个角色不出声 | 名字不对；面板会提示最接近的名字 |
| 一直很慢 | 免费 Space 在排队；桥接窗口会打印 `estimation rank=N queue_size=...` |
| 上游彻底下线 | 换 `--host` 指向别的 Space，或切回本地模式 |

## 上游服务说明

`zomehwh/vits-uma-genshin-honkai` 是社区 Space，页面自己标注
「严禁将模型用于任何商业项目」。它是**公共免费服务**，会排队、会休眠、可能随时下线——
所以本方案把它当作**可选增强**，而不是唯一路径：本地 GPT-SoVITS 始终可用。
