### 16.4.0.2 修掉的两个面板缺陷（用户实测反馈）

#### (1) 一点语音设置，宠物图片就变回默认图 —— **绑定返回值类型不匹配**

`SaveTTSSettings` / `StopSpeech` / `ClearTTSCache` 返回的是 **`SpeechView`**，
但前端一律写成 `App.X().then(applyState)`，而 `applyState` 期待完整的 **`State`**：

```js
function applyState(next) {
  state = next;        // ← SpeechView 整个覆盖了 State
  renderPet();         // ← state.petImageUrl === undefined → 回退默认图
```

所以**只要碰任何一个语音字段，宠物图片就被抹掉**。

**这是本方案自己的错**：既有绑定（如 `ChoosePetImage`）都返回 `State`，
我新加的三个没有遵守这个约定。Go 的类型系统在调用处看不出问题（都是 struct），
所以加了两条检查钉住它：

- `.dev/check-frontend.cjs`：断言 `App.d.ts` 里这三个方法**返回 `main.State`**
  （同时把 LLM 的两个也一起断言，免得以后修一个坏一个）
- `.dev/run-frontend-harness.cjs`：真实浏览器里**断言 `<img id="pet-image">` 的 src
  在保存语音设置后不变**

#### (2) 三个路径要手填 —— 改为**自动发现角色 + 浏览选择**

原来角色名、GPT 权重、SoVITS 权重、参考音频四个框都要手输，而这正是最容易错的地方：
路径长、含中文，填错会在合成时报服务端 `file not found`，**且不告诉你是哪个字段错**。

现在：

| 改动 | 说明 |
|---|---|
| **新增「角色文件夹」** | 指向 `models/` 目录（默认即 `tools/tts-p0` 装出来的那个），带「浏览…」 |
| **角色变下拉框** | Go 侧 `DiscoverVoices()` 扫描该目录，列出每个角色；**显示名优先取角色自己 `petpc-config.json` 里的中文标签**，文件夹名（`klee`）只是回退 |
| **选中即自动填三个路径** | 切换角色会**整体重填**，避免出现"gpt 是可莉、sovits 是纳西妲"这种会产出噪音却不报错的组合 |
| **缺文件的角色列出但不可选** | 灰掉并显示缺什么（如"缺 sovits.pth、ref.wav"），而不是让用户选中一个加载不了的音色 |
| **三个路径各加「浏览…」** | 带类型过滤（`.ckpt` / `.pth` / `.wav`） |
| **取消对话框不清空字段** | 对话框返回空串时直接 return；否则会把一个本来可用的路径抹掉 |
| **保留「自定义路径」** | 文件不在标准位置时仍可手填/手选 |

发现逻辑还**兼容手工整理的文件夹**：除了 `gpt.ckpt`/`sovits.pth`/`ref.wav`，
也认 `Klee-e10.ckpt`、`Klee_e8_s656.pth` 这类带 epoch 后缀的名字——
从模型仓库直接解压出来就是这种，不认的话用户会觉得"文件明明在却扫不到"。

**在真实目录上验证过**（`TestScanVoicesAgainstRealModelsDir`，读 `D:\GPT-SoVITS\models`）：

### 16.4.0.1 顺手修掉的一个既有崩溃 bug（重要）

实现设置面板时发现：**`llmView()` 与 `proactiveView()` 互相调用，形成无限递归**。

```
app_llm.go:217   llmView()       → a.proactiveView()   // 为了填 Proactive 字段
app_live.go:596  proactiveView() → a.llmView()         // 为了问 LLM 就绪状态
```

- **`llmProactive=false` 时不会触发**（`proactiveView` 在第 574 行提前 return），所以这个 bug 一直潜伏着
- **一旦在设置里打开「主动说话」，每次 `GetState` 都会递归到栈溢出**，进程直接死亡：
  `runtime: goroutine stack exceeds 1000000000-byte limit / fatal error: stack overflow`
- 表象是"应用启动后无声无息消失"，没有报错、没有日志、没有崩溃对话框 —— 极难凭现象定位

**修复**：抽出 `llmReadinessNow() llmReadiness` 返回 `{Ready, NotReadyReason, OverBudget}`，
`proactiveView` 改用它，依赖变成单向（`llmView` → `proactiveView`，不再回头）。

**回归测试**：`TestViewsWithProactiveOnDoNotRecurse`（`app_startup_test.go`）。
已实测验证：把 `a.llmReadinessNow()` 改回 `a.llmView()`，该测试立刻以
`fatal error: stack overflow` 失败；改回修复后通过。

> 这个 bug 与 TTS 功能无关，是既有代码里的，但**只有打开主动说话才会暴露** ——
> 而"打开主动说话"正是试语音时会顺手做的事。所以它成了 TTS 落地路上的拦路虎。

## 0. 一句话结论

**能在你这台机器上本地生成，但不是"系统 TTS 那种秒出"**，而是一句话大约 **1~5 秒**。

| 问题 | 结论 |
|---|---|
| 能本地跑吗？ | **能**。i5-11300H + 16G 内存 + 无独显，跑 GPT-SoVITS 的 CPU 推理是可行的 |
| 有加速指令吗？ | **有，而且是最好的情况**：实测你这颗 CPU **AVX-512 + VNNI 都可用**（Tiger Lake 多数型号会熔断，你这颗没熔断） |
| 和刚才那套系统 TTS 比？ | 系统 TTS 是 **105ms 出 28 秒音频**（约 266 倍实时）；原神音色是神经网络，**CPU 上估 RTF 0.6~1.5**，慢 2~3 个数量级 |
| 要装东西吗？ | **要**。PyTorch 无法链进 Go 二进制，必须跑一个 Python 旁路进程（这正是它"可选"的原因） |
| 能零依赖吗？ | **不能**。这是本方案与既有代码最大的不同：它引入了一个外部运行时 |
| 音质换来的代价 | 值得：系统 TTS 是"机器念稿"，原神音色是"角色说话" |

**你这台机器的三个硬约束（必须先解决，否则装不上）**

1. **物理内存只剩 4.3GB**（16GB 中已用 72%）—— 推理峰值约 2~4GB，勉强够，但必须关掉浏览器等大户
2. **系统 Python 是 3.13.2，GPT-SoVITS 只支持 3.10~3.12** —— 必须另装一个 Python，不能复用现有的
3. **F 盘只剩 13.5GB、C 盘 20.3GB** —— 整体需要 6~8GB，**装到 D 盘（剩 95.7GB）**

## 1. 为什么"原神 TTS"和系统 TTS 是两条完全不同的路

| | 系统 TTS（已放弃） | 原神音色 TTS（本方案） |
|---|---|---|
| 原理 | Windows 内置共振峰/拼接合成 | GPT-SoVITS 神经网络，从角色配音里学音色 |
| 依赖 | `SAPI.SpVoice`，系统自带 | Python + PyTorch + 数 GB 模型权重 |
| 音色 | 固定 3 个播音腔（慧慧/哈鲁卡/泽拉） | 任意角色，需要找/训练模型 |
| 速度 | 266× 实时（实测） | RTF 0.6~1.5（CPU，实测前估计） |
| 内存 | 几乎为 0 | 2~4GB |
| 安装 | 零 | 6~8GB、独立 Python 环境 |
| 数据出网 | 否 | 否（全本地） |

## 2. ⚠️ 先澄清：市面上的"原神语音模型"是**三种不同的东西**

**这条最容易踩坑，请先看**。你搜"原神 语音模型"时，**下载量最大、最出名的那批其实是变声器**：

| 类型 | 代表仓库 | 它做什么 | 输入 | 输出 | 能"把文字念出来"吗 |
|---|---|---|---|---|---|
| **GPT-SoVITS** | `xiaoheiqaq/GPT-Sovits-models`（心海） | 文字 → 语音 | **文字** | 语音 | ✅ **能** |
| **Bert-VITS2** | `edwin-yan/Bert-VITS2-Paimon-Chinese` | 文字 → 语音 | **文字** | 语音 | ✅ **能** |
| **so-vits-svc** | `kaze-mio/so-vits-genshin`（胡桃/可莉/纳西妲/瑶瑶） | **音色转换** | **一段人声** | 换成该音色的人声 | ❌ **不能** |

**`so-vits-svc` 是"变声器"**：你得先有一段别人说话/唱歌的录音，它把音色换成胡桃。它**不会**把"番茄钟结束了"这句话变成语音。

> 所以：**要"桌宠说话"，只能选 GPT-SoVITS 或 Bert-VITS2**。下错类型会白折腾几小时。

## 4. 架构

> **【下面是那一版的架构，已删除】**。保留它是因为它把"合成在 Go 侧、播放也在 Go 侧、
> 引擎是旁路进程"这条边界的理由说清楚了，而那几条理由（§4.1 / §4.2）现在依然成立，
> 只是承载者换成了插件：合成现在由**插件的 JS**发起（经 `net.fetch`），
> 播放由**宿主**执行（`audio.play`，同样走 winmm）。
> 也就是说"HTTP 出、winmm 回"这条链路还在，只是中间那层从 `internal/tts` 的流水线
> 换成了插件的 `app.js` + 宿主的 `audio.*`。

```
┌─ PetPC.exe（Wails / Go，单文件分发）─────────────────────┐
│  app_llm.go  流式回复 ──┐                                │
│                          ▼                                │
│  internal/tts/  切句器 → 合成客户端 → 播放队列             │
│                    │           │          │               │
│              (纯函数,可单测) │ HTTP       │ winmm          │
│                              │ POST /tts  │ PlaySound      │
└──────────────────────────────┼────────────┼───────────────┘
                               │            ▼
                    127.0.0.1:9880        扬声器
                               │
                 ┌─────────────▼──────────────────┐
                 │ GPT-SoVITS  api_v2.py           │ ← 旁路进程（Python）
                 │ 独立 venv + CPU 版 PyTorch       │
                 │ 角色权重 + 参考音频              │
                 └─────────────────────────────────┘
```

### 4.1 为什么必须是"旁路进程"，不能内嵌

PyTorch 无法链接进 Go 二进制。这打破了"PetPC.exe 单文件分发"的假设，所以 TTS 必须设计成**可选外部依赖** ——

> **这和现有的大模型端点是同一个哲学**：`LLMBaseURL` 填本机 Ollama 时，PetPC 就是"单文件 + 一个本地 HTTP 服务"。
> TTS 完全同构：**没配 / 没启动 / 报错，一律静默跳过朗读，番茄钟、提醒、待办、对话全部照常。**

### 4.2 为什么播放放在 Go 侧，而不是前端 `<audio>`

| 理由 | 说明 |
|---|---|
| **自动播放策略** | WebView2 会拦截"用户未交互过"的自动播放。而桌宠**主动说话恰恰不能要求用户交互**（`docs/llm-chat.md` §12.5 已经定了"主动说话绝不抢焦点"）——放前端必然踩这个坑 |
| **分层** | 前端只做渲染，这是项目已有的架构原则 |
| **打断简单** | 一次 `PlaySound(NULL,0,0)`，实测 **4ms** 停止 |
| **对像素约束零风险** | 音频不参与布局，`applyWindowGeometry` / 区域裁剪 / 三态互斥**一行都不用改** |

### 4.3 接口（已核实的 GPT-SoVITS API）

> **【这条仍然有效，但插件只用了其中一小部分】**。插件只用 `POST /tts`
> （见 `docs/voice.md` §5：一次请求一条台词，带全部采样参数）。
> **热切换那两个端点（`/set_gpt_weights`、`/set_sovits_weights`）现在没有人调**——
> 这是当前实现的一个**缺口**而不是设计选择：插件要求你填 `gptPath`/`sovitsPath`，
> 却从不把它们发给引擎，也从不调这两个端点，所以**渲染用的角色实际由引擎侧决定**，
> 与工坊左栏选中的那个无关（`docs/voice.md` §8 第 5 条）。
> 旧版靠这两个端点做到"切角色"，那条路径没有搬过来。

`api_v2.py`，FastAPI，默认监听 `127.0.0.1:9880`：

| 端点 | 用途 |
|---|---|
| `POST /tts` | 合成，返回 WAV 字节（支持 `text_lang` / `ref_audio_path` / `prompt_text` / `media_type=wav`） |
| `POST /set_gpt_weights` | 热切换角色 GPT 权重 |
| `POST /set_sovits_weights` | 热切换角色 SoVITS 权重 |

## 5. 核心设计：逐句流水线（CPU 方案能否可用的关键）

CPU 上合成速度 ≈ 播放速度（RTF≈1）。**如果等整段回复生成完再合成，用户要干等十几秒。**

所以必须三级重叠：**LLM 在流式产出时，就按句切，边合成边排队边播**。

```
LLM 流式 delta ──► 切句器 ──► 合成队列 ──► 播放队列
   边到边切              并发 1~2       顺序播放

时间轴（示意）：
t=0     用户发送
t=2s    第 1 句到达 → 送去合成
t=5s    第 1 句合成完 → 开始播放；第 2 句到达 → 送去合成
t=9s    第 1 句播完 → 第 2 句已就绪，无缝衔接
        ...
```

**用户感知到的延迟 ≈ 第一句的合成时间，而不是全文的合成时间。** 这是让 CPU 方案可用的唯一办法。

### 5.1 切句粒度（关键参数）

| 太短 | 太长 |
|---|---|
| 碎、请求多、句子间停顿明显 | 首句延迟大，流水线失效 |

建议 **12~28 字**，以 `。！？；\n` 为界，逗号作为"超长时的次级切点"。

### 5.2 只读前 N 句

默认 **3 句**。否则大模型一篇 500 字回复会被念 2 分钟，体验是灾难。

## 6. 播放、打断与缓存

### 6.1 播放

```go
// 写 WAV 到 <dataDir>\tts-cache\<sha1>.wav，再异步播放
procPlaySound.Call(pathPtr, 0, sndFilename|sndAsync|sndNoDefault)
```

- **打断**：`PlaySound(NULL, 0, 0)`，实测 4ms 停止当前播放
- **新回复到来**：清空队列 + 打断当前 + 重新开始

### 6.2 必须写进代码注释的坑

`SND_MEMORY` 播放时，**缓冲区必须在播放期间保持存活**被 GC 掉就会静音或崩溃。这与 `internal/desktop/sound_windows.go` 里已有的那条注释（为什么用 `MessageBeep` 而不是 `PlaySound(SND_ALIAS)`）**是同一类问题**。

**对策：一律走文件（`SND_FILENAME`），不用 `SND_MEMORY`。** 顺带白拿一个缓存。

### 6.3 缓存（白拿的收益）

内容哈希 `sha1(text + 角色 + 参数)` → WAV 文件。

- 番茄钟结束语、提醒文案、常见应答 **几乎全部命中**，命中即 0ms 出音
- 上限 LRU，默认 500MB

### 6.4 音量的限制

`PlaySound` **不能调音量**。要音量控制得换 `waveOutSetVolume`（设备级）或 MCI。**v1 不做音量**。

### 9.1 你的 CPU 实测（已完成，`.dev/tts-probe/cpuid`）

```
AVX512F      = true      AVX512BW   = true
AVX512VNNI   = true      AVX512VBMI = true
AVX512VL/DQ  = true      AVX2/FMA   = true
verdict: AVX-512 + VNNI present (best case for CPU inference)
```

**这是个好消息**：Tiger Lake 的多数型号把 AVX-512 **熔断了**，你这颗 `i5-11300H` **没熔断**。

- AVX-512 让向量宽度翻倍（vs AVX2）
- **VNNI** 是神经网络量化的专用指令，对 GPT-SoVITS 里的量化矩阵乘**直接加速**——这正是 CPU 推理最吃的那部分

**修正后的估计**：单核弱于 M4 约 2 倍，但 AVX-512 + VNNI 能补回相当一部分，且 4 核可并行。
**估 RTF ≈ 0.6 ~ 1.5，偏向乐观一侧** —— 所以大概率落在 §9 判定表的"✅ 可接受"档。

> 但仍**必须实测**：估算是估算，PyTorch 的 CPU 后端实际调度（线程数、MKL-DNN 是否走满 VNNI）只有跑起来才知道。P0 就是干这个的。

> 这步**不用改 PetPC 一行代码**，是纯外部验证。这也是本方案最省钱的一步。

## 11. 边界情况

| 情况 | 期望行为 |
|---|---|
| 旁路进程没启动 | **静默不朗读**，其余功能全部照常（与 LLM 未配置同一处理） |

## 14. 已知限制与风险

1. **版权**：原神语音资产版权属米哈游；社区模型多为"粉丝训练"的灰色地带。
   **不要把角色权重打进 PetPC 的发布包** —— 让用户自备，与本方案"可选外部依赖"的设计一致。

3. **无独显**：只能 CPU，速度是最大不确定性（§9 实测解决）。
4. **派蒙模型要自己找**：HF 上那个仓库没有权重。
5. **音质参差**：社区模型不同 epoch 效果差别大，需要试听挑选。
6. **不能调音量**（`PlaySound` 限制）。
7. **分发变复杂**：从"一个 exe"变成"一个 exe + 一个可选 Python 服务"。接受这一点，或者只做 P6 台词库。

### 16.2 与本文档原设计的差异（实现时改的）

| 原设计 | 实际实现 | 原因 |
|---|---|---|
| 单个 worker 边合成边播放 | **合成 / 播放两个 worker**，用带缓冲 channel 交接 | 单 worker 会让合成串在播放等待之后，**完全丧失重叠**——用户仍要等整段回复。这是本项目最大的一个实现修正，且专门有测试 `TestPipelineOverlapsSynthesisWithPlayback` 钉住它 |
| `MaxSentences` 队列深度固定 3 | **输入 channel 缓冲 = `MaxSentences`** | `Add` 跑在 chat 流 goroutine 上；缓冲小于句子上限时它会阻塞，**进而卡住模型流本身**。按上限开缓冲让阻塞在结构上不可能（`TestPipelineAddIsNonBlocking`） |
| `Flush` 后即可 `Close` | 拆成 **`Flush` + `Wait`（排空）+ `Close`（打断）** | 二者语义相反：一个说"把剩下的说完"，一个是"立刻停"。合并必然做错一个 |
| 需要一个导出测试钩子替换播放器 | **不导出**，测试在同包内直接赋值 | Wails 会绑定 App 上**每一个导出方法**——导出钩子会把它连同 `tts.Speaker` 类型一起暴露进前端绑定（实测确实泄漏了，已修） |
| 缓存实例创建一次 | **配置变化时重建** | 预算可以在面板里改；持有旧实例会导致"关了缓存却仍全部命中磁盘"（`TestSpeechNoCacheBudgetZero` 抓到的真 bug） |

### 16.3 测试逼出来的真实缺陷

1. **`Flush` 静默丢弃句尾** —— 它走了 `nextChunk`，而后者在无终止符时返回"还不能切"。结果：不以标点结尾的回复，最后一句**永远不被朗读**，桌宠无缘无故停顿半句。改为无条件 flush。
2. **`Add` 会阻塞** —— 小缓冲 channel 在合成跟不上时阻塞调用方，也就是**卡住模型流**（实测阻塞 23 秒）。按句子上限开缓冲后结构性消失。
3. **超时被误判成"已取消"** —— 同一个 context 错误既能是超时也能是取消，`ctx.Err()` 判空就归类会让**超时永远不被记录**。改为先判 `Canceled`、再判 `DeadlineExceeded`。
4. **并发下音色重复加载 32 次** —— check-then-act 竞态（只锁了读）。CPU 上每次加载数秒，且会互相争抢。改为整个"检查+加载"持锁。
5. **HTML 错误页漏进气泡** —— 端口指错服务（路由器后台等）时返回 HTML，未清标签会整页塞进 300px 气泡。
6. **缓存把临时文件算进预算** —— 临时片段也叫 `.wav`，会虚增体积并触发无谓淘汰；改为按 SHA-1 文件名形状精确识别。
7. **缓存计数写坏** —— 修 (6) 时引入 `over` 恒为 false，缓存**永不淘汰**、无限增长。由 `TestCacheEvictsWhenFullEvenWithoutReuse` 抓出。
8. **`trimTTSPath` 漏掉尾斜杠** —— `http://…/tts/` 会存成 baseURL `…/tts`，客户端再拼一次变成 `/tts/tts` → 404，而面板显示完全正确。
9. **导出测试钩子泄漏到前端绑定** —— 见 §16.2，`wails build` 后检查 `App.d.ts` 发现。

> 还有一条**测试自身**的问题：我用 PowerShell 正则批量改测试文件时打乱了 UTF-8，导致 37 处中文变成非法字节。教训是**改文件一律走文件工具，不用 shell 文本替换**——这个项目的源码全是中文注释，shell 重写极其危险。

这一节记录的是**实测踩出来的坑**，每一条都花了时间才定位。按重要性排序：

#### (1) 选模型看**训练语料语言**，不是看角色说什么语言

`xiaoheiqaq/GPT-Sovits-models` 的心海模型：角色是中文角色、仓库还放了中文样例音频，
但 README 写着 **"Trained on ~1hr of english voiceover data"**（英语配音训练）。
拿它合成中文，**实测完全不像心海**。

**我把它写进文档说"中文可用"，这是错的。** 换用
`BigPancake01/GPT-SoVITS_Mihoyo`（README 明确「使用…角色的**对话语音**训练」、
语言标注 `zh`）之后才正常。

> **换模型判据**：看 README 的 `Trained on ...` 与 HF 的 `language:` 标签，
> 不要看角色国籍，也不要被仓库里的中文样例音频误导（样例可能只是跨语言演示）。

#### (2) `prompt_text` **宁可不填，也不要猜**

`prompt_text` 是参考音频的**逐字转录**。GPT-SoVITS 用它对齐参考音频；
**填错比不填更糟** —— 模型会照着错误的文本去匹配声学特征，输出直接退化。

实测：我猜了一句「炸弹？嘿嘿，可莉最喜欢炸弹了！」（里面还含"嘿嘿"），
结果是**整段都在笑、几乎不成词**。同一段参考音频**留空 `prompt_text`** 就完全正常。

**这是 PetPC 代码的一个真 bug**：`TTSConfigured()` 原来要求 `TTSPromptText` 非空，
否则拒不出声——等于**强迫用户去猜一个转录**，而猜错比留空更糟。
现已修正为只需参考音频。注释里那句"GPT-SoVITS 需要它"也是错的，一并改掉。

#### (3) 参考音频开头必须**干净**（否则会被克隆成"前置语气声"）

症状：每句开头多出约 0.1~0.5 秒的**短促语气声**（像吸气/轻哼），停顿一下才正式说话。

**不是杂音、不是爆音、不是蓝牙问题**——是**参考音频开头那段被忠实克隆了**。波形证据：

```
可莉 输出: 1501 → 3291 → 5401 → 6161 → 2267 → 175 → …静音… → 正式说话
可莉 参考:   43 → 2578 → 5069 → 5652 → 3532 →  141 → …          ← 形状一致
```

**处理**：裁掉参考音频开头那段（见下）。**不要在播放侧加淡入**——
淡入虽然听不见那一下，但会**把开头的真实音节一起削掉**，治标还伤本。

已裁：可莉 0.32s、绫华 0.22s、宵宫 0.52s（纳西妲开头本来就干净，裁 0s）。
原始文件保留为 `ref_original.wav` 可回退。

| 排除过的假设 | 检验结果 |
|---|---|
| 音频削波/爆音 | 削波数 **0**，峰值正常 |
| 起始不连续 | 静音→满值约 20ms，平滑 |
| 底噪/嘶声 | 合成输出底噪 **0** |
| 参考音频残留 | 互相关 **−0.16~+0.03**（无关） |
| 蓝牙链路唤醒 | 连播 3 次现象一致 → 不是链路 |

1. **RTF 0.894 意味着"边生成边朗读"仍然可行，但余量不大** —— CPU 合成比播放快约

4. **冷启动 10 秒**：PetPC 应在启动时做一次后台预热（对 `/tts` 发一个空请求），

## 17. 在线模式（P7，已实现）

### 17.1 为什么加它

本地 GPT-SoVITS 的两个硬伤，在线模式都能绕开：

| | 本地 | 在线 |
|---|---|---|
| 可用音色 | 你下载的那几个 | **804 个，其中原神中文 97 个** |
| 本机内存 | **3.3 GB** | 桥接进程约 **30 MB** |
| 冷启动 | 10.3 秒 | 首次约 1~3 秒 |
| 依赖 | 自己装 4.7GB 环境 | 一个 Python 进程 |
| 代价 | — | 公共免费服务，会排队/休眠/下线 |

### 17.2 关键设计：**桥接**，而不是在 Go 里实现两套协议

`tools/tts-online/bridge.py` 在本机发布一个**与 GPT-SoVITS 完全同形**的接口
（`/tts`、`/set_gpt_weights`、`/set_sovits_weights`），背后代理公共 Space。

**结果是 PetPC 的客户端一行都没改**：切句器、WAV 缓存、打断、播放流水线、错误分类
全部照用。两个后端唯一的差别被压缩进 `app_tts.go` 的 `ttsSettings()` 和
`store.TTSActiveURL()` 两处：

| 差异 | 本地 | 在线 |
|---|---|---|
| 地址 | `127.0.0.1:9880` | `127.0.0.1:9881`（**不同端口，可同时运行**） |
| 音色标识 | 参考音频 + 两个权重的**路径** | 音色**名字**（服务端拥有模型） |
| 音色列表来源 | 扫描 `models/` 目录 | 问桥接的 `/voices` |

> 上游用的是 **Gradio 3.7 的 WebSocket 队列**（三步握手）。
> 在 Go 里实现意味着自带 WebSocket 客户端 + 手写队列协议，换不来任何好处；
> 而放进 Python 后，"上游下线"最多只坏这一个文件。

### 17.3 上游的三个坑（全部实测踩过）

#### (1) 一次最多 100 字，超了**完全不出声**

```
 66 字 -> 12.42s   ✅
110 字 -> FAIL: "输入文字过长！110>100"   ❌ 没有音频
```

桥接**不静默截断**，而是返回明确错误——静默截断会让桌宠念半句话，用户只会以为"卡了"。

> 这条正好证明**切句是必需的**：PetPC 默认按 ~20 字切句，天然满足；若关掉切句直发整段就会撞上。

#### (2) 角色名错了**不报错，只是返回空音频**

`纳西妲` 不行，必须写 `纳西妲（草神）`。桥接为此返回可操作提示：

```
在线服务不认识「不存在的角色xyz」这个名字。请从下拉列表里选（该服务有 804 个音色）
```

#### (3) 协议是三步握手，且**每个任务要独立连接**

```
1. 连接 → 收到 {"msg":"send_hash"}
2. 发任务 → 收到 estimation → {"msg":"send_data"}
3. 再发一次同样的任务 → process_starts → process_completed
```

POST `/api/predict` 会返回 `401 "Not authorized to skip the queue"`——
这个 401 是**关键线索**：说明路径存在、只是被故意拒绝，从而指向队列协议。

另外**参数顺序是组件 ID 而非数组位置**：`inputs=[6,7,13,15,16,17]` 对应
`[文本, 语言, 角色, 三个滑块]`。顺序错了会"成功"但输出为空——这个坑浪费的时间最多。

> 自己不发 HTTP 之外的任何东西，也不区分"在线/本机"——见 `docs/voice.md` §5。

面板会把本地才需要的字段（角色文件夹、三个路径、参考文本）**自动隐藏**，
切回「本机」时又出现——因为两套配置完全不同，同时显示只会让人去填用不上的字段。

详见 `tools/tts-online/README.md`。

### 17.6 关于"几个角色没说全"的澄清

用户反馈"有几个角色的语音没说全"。**查下来是我的演示脚本的问题，不是服务截断**：
两批样本用了**不同长度的文本**（三个是 31 字长句、三个是 10 字短句），连着听就像后三个被截断了。
用**同一句 54 字**重测 6 个角色后，全部完整（都约合 51~61 字）。

真正的截断风险来自上面 §17.3(1) 的 **100 字硬上限**，已由切句和桥接的显式报错覆盖。

## 18. 长句拆分与音画对齐（P8，已实现）

用户反馈两条，都做了：

> 长句有时候会不全，把长句分成两句来生成，同时生成的回复需要和语音生成对齐，
> 现在的语音生成都比文字生成慢，不要先显示文字，等语音生成完毕后再来一起显示。

### 18.1 "长句不全"——**实测确认是真的，不是错觉**

一开始我怀疑是随机性：上游页面自己写着「结果有随机性，可多次生成取最佳效果」，
而第一次对比里同一分组两次跑出 93.1% 和 100% —— **差别在波动范围内**。
在此基础上做修改等于基于噪声。

所以做了**重复测量**（每组 3 次，同一段 38 字，只改分组方式）：

| 分组 | 平均音频 | 相对 |
|---|---|---|
| 1 次请求（38 字） | **7.74s** | — |
| 2 次请求（24+14） | 8.08s | +4.4% |
| 4 次请求（12 字） | **8.28s** | **+6.5%** |

单次运行的波动只有 **0.48~0.63s**，而差距是 **0.54s 且随分组长度单调变化** ——
**结论：长请求确实会丢内容，拆句能拿回来。** 复现脚本：`.dev/tts-probe/ws_noise.py`。

### 18.2 硬上限：单次最多 ~100 字，超了**完全不出声**

```
 66 字 -> 12.42s   ✅
110 字 -> FAIL: "输入文字过长！110>100"   ❌ 没有任何音频
```

这不是"读得差一点"，而是**整句静默消失**。原有切句器的问题是它的上限**随设置缩放**：

```
max = target × 4   （target 就是面板上的「每句字数」）
```

于是用户把「每句字数」调到 50，上限就变成 200 字 —— **每一句都会被服务拒绝**。
所以上限必须是**服务端的属性**，不能是滑块的衍生值：

| 后端 | 单次上限 | 来源 |
|---|---|---|
| 本地 api_v2.py | 无特别限制 | 由 target 推导（原行为） |
| 在线桥接 | **90 字** | `store.TTSOnlineMaxChunkRunes`，服务硬限 100，留 10 字余量 |

新增 `NewSplitterCapped(target, maxChunk)`：**只允许收紧，不允许放宽** ——
安全上限 `absoluteMaxChunkRunes` 仍然是最后一道闸，否则一次请求体可以无界。

### 18.3 音画对齐：文字跟着语音走

问题在于**合成比生成慢**（这台机器上尤其明显），所以按原来那样边生成边显示，
用户会**先读完一整段答案**，而桌宠还在念第一句 —— 看起来文字和声音毫无关系。

现在：**语音开启时，回复文字不流式显示**，而是被 `holdText` 扣住，
由流水线在**每一段音频即将播放之前**逐句释放。

选的是**逐句对齐**（每句生成完就显示这句），不是"整段等完再一次显示"——
后者会让界面空白十几秒。

#### 为什么用「前缀」而不是「增量」

流水线报的是**到目前为止已播放文本的完整前缀**，不是"这次多出来的几个字"：

- 接收方只需**赋值**，不必拼接，天然不怕事件重复或乱序
- 前缀由**真正播放过的片段**拼成，不是由切句器的输入拼成 —— 这两者在关键场景下不同：
  **合成失败的句子会从音频里消失，超出句子预算的文字根本不会被朗读**，
  用输入拼就会出现"屏幕上有、耳朵里没有"

#### 为什么不会丢文字

这是整套机制的前提。有四种**正常**情况会让文字没被朗读：

1. 句子预算截断（`ttsMaxSentences`）
2. 某段合成失败
3. 用户按了停止
4. 语音服务根本没开

所以 `finishSpeech` 在**朗读排空之后**必定调用 `revealRemaining`，
把完整回复发出去。测试 `TestRevealEndsWithTheWholeReply` 专门盯这条：
3 句回复、只朗读 2 句，第 3 句**仍须出现**。

#### 顺序很讲究

- `reveal` 在 **`PlayWAVFile` 之前** —— 放在之后文字就落后声音一句
- `revealRemaining` 在 **`p.Wait()` 之后** —— 放早了会在语音还在念前面时把尾巴全显示出来

#### `speechGated` 标志

`done` 事件可能**早于**第一次 reveal 到达（首句还在合成中）。
此时前端无法区分"还没 reveal"和"语音没开"，猜错会导致：
**要么把已完成的回复藏在静默服务后面，要么把正在朗读的回复一次性全显示**。
所以 `done` 显式带上 `speechGated`，前端据此决定是否等待。

## 19. 番茄钟与待办提醒的朗读（P5，已实现）

让桌宠在**番茄钟阶段结束**和**待办提醒弹出**时开口。这两处和朗读回复**不是一回事**，
所以走了一条独立的路径 `SpeakLine`。

### 19.1 为什么不能复用回复的流水线

| | 朗读回复 | 朗读通知（P5） |
|---|---|---|
| 文本来源 | 模型流式产生，**边生成边切句** | 完全已知，一次给全 |
| 音画对齐 | **必须**扣住文字逐句释放 | 不需要——气泡/面板已经显示 |
| 句子预算 | 用户设定（默认 3 句，会截断） | **固定 8 句**，通知不能被截半 |
| 调用线程 | 请求 goroutine | **定时器回调 / 布局路径** |

最后一条是关键：`SpeakLine` 会在**持有 `pomoMu` 时被调用**，
所以它必须立即返回、在后台念完。阻塞任何一边都会冻住倒计时或窗口。

> **`SpeakLine` 绝不碰 reveal 记账**（`reqID`/`pending`/`revealed`）。
> 通知可能正好落在一条回复**正在逐句显示**的中间；如果通知清掉了 round id，
> 那条回复剩下的句子就**不会再显示**，被扣住的文字会一次性全冒出来。
> 测试 `TestNoticeDoesNotDisturbTheRevealRound` 专门钉这条（已变异验证）。

### 19.2 四个开关，默认值**故意不同**

| 开关 | 默认 | 理由 |
|---|---|---|
| 朗读对话回复 | 开 | — |
| 朗读主动说的话 | 开 | 本来就限 80 字，最适合朗读 |
| **朗读番茄钟提示** | **开** | 用户**自己启动**的计时，正在等它结束，开口是预期之内的 |
| **朗读待办提醒** | **关** | 提醒可能在**开会时**才触发，桌宠突然出声比气泡滑入侵入性强得多 |

因为默认值不同，前端两个复选框的**比较运算符也必须不同**：

```js
els.ttsReadPomodoro.checked = cfg.ttsAutoReadPomodoro !== false;  // 默认开
els.ttsReadReminder.checked = cfg.ttsAutoReadReminder === true;   // 默认关
```

两处都写 `!== false` 会把**所有既有配置的提醒朗读静默打开**，正好与设计相反。

### 19.3 顺手修掉的一个既有 bug：四个复选框**全是摆设**

做 P5 时发现：面板渲染了「朗读对话回复」「朗读主动说的话」，
`ttsSettingsPayload()` 却**从来没有把它们发出去**，`SaveTTSSettings` 也**从来没有持久化它们**。

也就是说 —— **这四个开关点了没有任何作用**：界面显示一个状态，配置里从未改变。
比"少一个功能"更糟，因为用户以为自己已经关掉了。

修法：`SpeechView` 增加四个字段 → 载荷发送 → Go 侧持久化 → 视图回传。
`TestAutoReadSwitchesRoundTrip` 盯这条（已变异验证：去掉持久化立刻失败）。

> **注意契约**：`SaveTTSSettings` 的入参是**整个表单**，"一一对应"是**字面意思**——
> 没传的布尔值会被写成 `false`。所以想关掉某个开关是可行的（这是更常见的方向），
> 但只想改一个路径的调用方必须把四个开关一起传。前端一直是全传的。
> 这个契约已写进函数注释，因为它是"改一个路径结果把朗读关了"这类 bug 的根源。

### 19.4 挂点与顺序

```go
// 番茄钟：阶段结束（app_pomodoro.go）
if out.EndedPhase == store.PhaseFocus {
    a.playPhaseSound(store.PhaseFocus)   // 系统音（已有）
    a.speakPomodoroLine(store.PhaseFocus)  // 朗读（新增）
    ...
}

// 提醒：气泡弹出之后（app_reminder.go）
a.showBubble(&BubbleView{...})
stats := a.store.Stats()
a.speakReminderLine(stats.DueSoon, stats.Overdue, stats.Open)
```

**提醒是"先弹气泡、后朗读"**：反过来的话，合成慢会**推迟视觉通知**——而视觉通知才是用户要照做的东西。
这一点由 `check-frontend.cjs` 用**位置比较**（而非脆弱的正则）钉住。

报的是 `Stats` 里的计数，不是气泡里的条目数：气泡被 `ReminderMaxItems` 截断，
按条目数念会**少报**。

### 19.5 措辞是"桌宠在说话"，不是计时器字幕

朗读的意义在于用户**正在看别处**，所以话必须脱离视觉上下文也成立：

| 场景 | 说出口的话 |
|---|---|
| 专注结束 | 「专注时间结束了，起来活动一下吧。」 |
| 休息结束 | 「休息结束了，我们继续吧。」 |
| 有逾期 | 「有 N 件事情已经逾期了，记得看一下。」 |
| 今天到期 | 「今天有 N 件事情到期，别忘了。」 |
| 其他 | 「你还有 N 件待办没有完成。」 |
| 空列表 | **不出声**（"没事可报"不值得一句话，在线后端还白占一次排队） |

测试专门断言**不出现计时器数值**（`%`、"分钟"）——念数字既没用又突兀。

### 19.6 实测验证

## 20. ~~按标点切到 15 字以内~~ → **已作废，见 §22**（P9，误判）

> **本节结论是错的，保留作为记录。** 用户的原始反馈是"超过 15 个字语音就可能会被截断，
> 所以按照逗号和句号，如果超过 15 个字，那就从逗号开始分割"。我照做了，**结果更糟** ——
> 用户随后反馈"完全就是断掉的一句话"。真正的病因在 §22：**在逗号处切分**本身。

用户反馈：

> 超过 15 个字语音就可能会被截断，所以按照逗号和句号，如果超过 15 个字，那就从逗号开始分割。

### 20.1 先说一件重要的事：**我的测量和用户的听觉不一致**

我试了三次想证实这个 15 字阈值，**三次都得不到支持**。同一段 55 字，
只改请求的分组方式（词完全一样）：

| 分组 | 音频 | 每 100 字 |
|---|---|---|
| 1 次（55 字） | 11.77s | **21.40s** |
| 2 次（~28 字） | 10.88s | 19.78s |
| 4 次（~14 字） | 10.88s | 19.79s |
| 8 次（~7 字） | 10.23s | 18.61s |

**请求越短，音频反而越少** —— 这与"长请求被截断"正好相反。
而 §18.1 里同一个指标曾在另一段文本上**给出一致方向的结果**（拆开多 6.5%）。
同一个指标在两次实验里指向相反方向，说明**"音频秒数"不是一个可信的截断指标** ——
很可能混入了服务在短请求上的停顿填充。

**当时的决定**（现在看是错的）：既然指标不可信、而用户亲耳听过，就按 15 字实现，
理由是"改动便宜可逆，最坏情况是多几次请求"。

> **这里漏掉了一种可能：用户的描述正确，但归因错误。**
> 用户听到的确实是"被截断"，但病因不是**长度**，而是**切分位置**（见 §22）。
> 我当时只考虑了"用户对 / 测量对"两种可能，没有考虑"现象对、归因错"这第三种。
> 而"便宜可逆"这个理由让我**跳过了一次本该做的对照实验**：
> 把同一句话按逗号切 vs 按整句切，直接放给用户听。那个实验后来只花了十分钟，
> 而且**一次就定案**。

**记录在此，供日后复查。** 判定阈值真正可靠的指标应该是**语音识别回读**
（把合成结果转文字，看尾巴是否丢失），而不是时长。本轮没有做。

### 20.2 真正的缺陷：到上限时**硬切在字中间**

即使不谈阈值，原有逻辑本身就有问题。达到上限时它**直接在上限处切断**：

```go
if seen >= max {
    cut = i + 1   // ← 落在词中间
```

切在词中间，服务就会丢掉句子尾巴 —— 听起来就是"卡住/没念完"。
**正确做法是退回最近的一个标点**，因为那里本来就是说话人会停顿的地方。

新规则（`nextChunk`），按优先级：

1. **硬标点**（`。！？`）立即成句，不论位置
2. **软标点**（`，、；`）达到 target 即成句
3. **达到上限** → **退回最近的标点**，而不是切在上限处

第 3 条的退回**有下限**：只有在标点落在后半段时才退回。
否则「好，然后……」这种开头一个逗号的情况会切出 2 个字的请求，
**一串超短请求比那次硬切更碎**。

### 20.3 阈值与实现（**已作废**）

```go
TTSOnlineMaxChunkRunes = 15   // ← 已改回 90，见 §22
```

同时 `NewSplitterCapped` 把 target 也压到 cap 以内（防御性，见代码注释）。

实测输出（`go run .dev/tts-probe/show_chunks.go`）—— **这就是问题的样子**：
每一段都以**逗号**结尾，都是**半句话**。

```
原文 (29 字): 今天天气不错，我们去公园散步，顺便买点水果，晚上回来做饭。
    [15 字] 今天天气不错，我们去公园散步，
  └ [14 字] 顺便买点水果，晚上回来做饭。

原文 (16 字): 专注时间结束了，起来活动一下吧。
    [ 8 字] 专注时间结束了，
  └ [ 8 字] 起来活动一下吧。

原文 (41 字): 你一共有五件待办，其中两件今天到期，上午的复习计划还没有开始，下午三点有一个会议。
    [ 9 字] 你一共有五件待办，
    [ 9 字] 其中两件今天到期，
    [13 字] 上午的复习计划还没有开始，
  └ [10 字] 下午三点有一个会议。

原文 (33 字，无任何标点):
    [15 字] 这是一个很长的从句它一直都没有
    [15 字] 出现任何标点符号所以只能靠长度
  └ [ 3 字] 来切分
```

**每段 ≤15 字，断开处都是逗号或句号**；只有完全无标点的文本才退回按长度切。

**真机验证**（桥接 + 可莉音色，41 字长句）：

```
[ 9字] HTTP 200  1.39s  你一共有五件待办，
[ 9字] HTTP 200  1.67s  其中两件今天到期，
[13字] HTTP 200  1.87s  上午的复习计划还没有开始，
[10字] HTTP 200  1.31s  下午三点有一个会议。
```

### 20.4 一个**没能通过变异测试**的教训

第一版 `TestOnlineChunksBreakAtPunctuation` 用的样本文本恰好**逗号就在第 15 字**。
于是规则 2（逗号达 target）先触发，**第 3 条的退回逻辑根本没执行** ——
把退回改成硬切，**测试依然通过**。测试是绿的，但它**没有验证它声称验证的东西**。

重写后用了逗号在第 13 字的样本，变异立刻被捕获：

```
--- FAIL: TestSplitterBacksUpToPunctuationAtTheCap
    first chunk = "一二三四五六七八九十甲乙，丙丁", want it to end at the comma
    first chunk is 15 runes, want 13 (up to the comma)
```

另外 `target` 压到 cap 以内那一处，**变异测试证明它是冗余的**（有了退回规则后，
删掉它行为不变）。所以代码注释里**标明它是防御性的、不是承重的**，
对应测试的注释也写明它**不能**隔离这个分支 —— 免得后人以为那行是必需的。

> 两次变异"幸存"都是同一个原因：**用错误的方式做替换**（换行符不匹配）导致变异根本没写进去。
> 所以看到变异通过时，**先确认变异真的生效了**，再下结论。

### 20.5 新增测试

| 测试 | 钉住的行为 |
|---|---|
| `TestSplitterBacksUpToPunctuationAtTheCap` | 到上限**退回逗号**（变异已验证） |
| `TestSplitterFallsBackToHardCutWhenPunctuationIsTooEarly` | 标点太早时**不退回**，避免超短请求 |
| `TestOnlineChunksStayWithinTheReportedLimit` | 在线后端任何一段都 ≤15 字，且不丢字 |
| `TestOnlineChunksBreakAtPunctuation` | 除最后一段外都以标点结尾 |
| `TestTargetIsLoweredToTheCap` | target 远大于 cap 时仍满足上限 |
| `TestShortTextIsNotOverSplit` | 本来就短的不被切碎 |
| `TestLocalBackendIsUnaffected` | **本地后端不受影响**（这是在线服务的限制） |
| `TestUnpunctuatedRunIsStillBounded` | 完全无标点也受上限约束 |

### 20.6 顺带修掉一个**偶发**的像素断言

全量门禁里 `the panel rectangle is unchanged by the speech section` **失败了一次**：

```
{"x":160,"y":0,"width":380,"height":520}
vs
{"x":160,"y":4,"width":380,"height":520}
```

**x、width、height 完全相同，只有 y 差 4px** —— 而这一轮我**只改了 Go 代码**，
前端产物字节未变（`index-65559097.js` 时间戳早于本轮全部改动）。
连跑 3 次又全过，确认是**偶发**。

**成因**：那条断言把两件事混在一起了 ——

- **尺寸**不变：这是**真正的**不变量，原生窗口区域就是按这个矩形裁的
- **位置**不变：面板是相对桌宠摆的，重新打开面板本身就可能让桌宠挪几个像素

断言位置是**过严**，不是发现了 bug。改为只比尺寸后连跑 4 次全过。

> 一个会偶发失败的检查比没有检查更糟：它训练人忽略红灯。
> 所以这里不是"重跑一下算了"，而是把断言收紧到**真正承重的那一半**。

## 21. 整段生成完再朗读（P10，已实现）

用户反馈：

> 一句一句发出来太奇怪了，不如等全部生成完再发出来。

### 21.1 为什么逐句播放听起来"奇怪"

每一段音频都是**一次独立的合成请求**，所以每一段都有自己的语调起伏，
两段之间还必然隔着**下一次合成的时间**（在线模式 1~2 秒，本地更久）。
连起来听就是「一句。……一句。……」，像在念清单，而不是在回答。

### 21.2 实现：先收齐，再播放

新增 `Options.WholeReply`：**所有片段合成完再开始播放**，文字也一次性显示。

```go
clips := p.gatherClips()        // 收齐全部
if len(clips) == 0 || p.ctx.Err() != nil { return }
p.revealAll(clips)              // 文字一次性出现
for _, c := range clips { ... } // 连续播放
```

**不会死锁**：合成 worker 推进缓冲通道，播放侧在通道关闭前持续消费，
不存在"worker 等满缓冲、而没人读"的环。

### 21.3 代价说清楚

| | 逐句（旧） | 整段（新） |
|---|---|---|
| 第一声 | 第一句合成完就出声 | **整条回复**合成完才出声 |
| 听感 | 像念清单 | **像一句话** |
| 总耗时 | 相同（合成本来就是串行的） | 相同 |

旧模式的"重叠"只是把合成藏在播放背后，而这台机器上**时间并不花在播放上**，
所以重叠省不下多少。实测：54 字回复，**热缓存 11 秒**（冷启动 36.7 秒含排队）。

> **短通知（P5）仍然逐句播放**，这是刻意的：通知只有一句、通常已在缓存里，
> 先收齐不会更快、只会更晚 —— 而计时器/提醒**晚到就等于没到**。

### 21.4 顺带把句子预算从 3 句提到 8 句

实测发现：54 字的回复**只念了 31 字** —— `ttsMaxSentences = 3` 把后两句丢了。
这和整段模式**叠加**后特别别扭：用户已经付了全部合成的等待，却只听到一部分，
而且**文字会在声音停止之后才长出后半截**。

默认值改为 **8 句**，仍然是上限（500 字的长回答全念要几分钟，那比不念更糟）。

### 21.5 一个**做错了又撤回**的改动

我一度想让「第一次 reveal 就显示完整回复」，这样文字不会在声音停下后再长出来。
为此在 `onSpeechProgress` 里加了"若 `speech.full` 更长就用它"。

**诊断直接打脸**：

```
DIAG reveal="第一句在这里。第二句在这里。" full=""
```

`full` 是**空的**。查下去才明白这不是时序问题，而是**根本不可能**：

> 句子预算用尽时，`Pipeline.enqueue` 会**立即关闭输入并开始播放** ——
> 这可以发生在**模型还在流式输出**的时候。那一刻，回复的后半部分**还不存在**。

所以"提前显示完整回复"在预算触发时**物理上做不到**。
改动已撤回，`revealRemaining`（最终 reveal 补发全文）确认是唯一正确的路径，
测试也改成断言**这个真实可达的行为**，而不是我原本想象的行为。

> 教训：**先诊断，再改**。两行 `DIAG` 打印比反复读代码快得多，
> 而且直接推翻了我在注释里写得很自信的一段推理。

### 21.6 实测（真实在线服务）

```
synth  [13字] 今天是十月二十四日星期五，
synth  [ 9字] 你一共有五件待办，
synth  [ 9字] 其中两件今天到期。
synth  [13字] 上午的复习计划还没有开始，
synth  [10字] 下午三点有一个会议。
REVEAL (54 字) ← 全文一次性出现
PLAY ×5        ← 然后连续播放
```

**顺序断言**：所有 synth 都在第一个 PLAY 之前 —— 由探针
`.dev/tts-probe/verify_wholereply.go` 与 `internal/tts/wholereply_test.go` 双重确认。

### 21.7 新增测试

| 测试 | 钉住的行为 |
|---|---|
| `TestWholeReplyPlaysEverythingAfterSynthesisingEverything` | **全部合成完才播放**（变异已验证） |
| `TestWholeReplyRevealsOnce` | 文字只 reveal 一次，且是全文（变异已验证） |
| `TestWholeReplyLosesNothing` | 收齐过程不丢片段、不丢字 |
| `TestWholeReplyRevealMatchesWhatIsPlayed` | 合成失败的句子**不出现在**文字里 |
| `TestWholeReplyStopsBeforePlayingOnCancel` | 停止后**一个字也不播** |
| `TestPerSentenceModeIsUnchanged` | 逐句模式仍然重叠（通知依赖它） |
| `TestWholeReplyEmptyIsHarmless` | 纯标点输入不出声 |
| `TestUnspokenTailArrivesWithTheFinalReveal` | 未朗读的文字**最终仍显示** |

**变异测试**：让 `WholeReply` 失效退回逐句 → 两项测试失败（已实测确认）。

> 写 `TestPerSentenceModeIsUnchanged` 时踩了一个坑并写进了注释：
> 用**瞬时**合成器时，合成 worker 会把 3 深的缓冲**全部填满**才轮到播放，
> 于是逐句模式也表现成 `synth synth synth play play play` ——
> 测试因为**与模式无关的原因**失败了。给合成器加上延迟，重叠才可观测。

## 22. 真正的病因：**每个片段都是残句**（P11，已实现）

用户对我上一轮实现的评价只有一句：

> 完全就是断掉的一句话，问题很大

### 22.1 三个假设，逐个排除

| 假设 | 测什么 | 结果 | 判定 |
|---|---|---|---|
| 接缝处静音太多 | 每段首尾静音 | 每处仅 **0.07s** | ❌ 太短，不足以"断掉" |
| 切点落在词中间 | 断点字符 | 都落在**逗号** | ❌ 位置本身不算错 |
| **每段是残句** | 后端收到的文本 | 「今天是十月二十四日星期五，」 | ✅ **病因** |

第三个假设是**唯一能同时解释两件事**的：用户两次反馈（"超过15字会截断" / "完全断掉"）
其实是**同一个现象**，而我三次测量都测不出"截断"—— 因为**问题不在长度，在于
每个请求都是不完整的句子**。

### 22.2 决定性实验：让用户直接听 A/B

我不再争论指标，而是**渲染同一条回复的两个版本**，拼成单个 WAV，请用户听：

| | 切法 | 段数 | 每段内容 |
|---|---|---|---|
| A | 按逗号（当时实现） | **5** | `今天是十月二十四日星期五，` ← 残句 |
| B | 按整句 | **2** | `今天是十月二十四日星期五，你一共有五件待办，其中两件今天到期。` |

用户回答：

> **后者更正常，切5句【】拼接反而有些奇怪。**

**十分钟定案**，而在此之前我已经在错误方向上做了三轮测量和一次实现。

### 22.3 为什么残句必然难听

TTS 模型对**完整句子**会生成句末语调（降调、拖长、停顿），这是"说完了"的声学标志。
给它一个以逗号结尾的**片段**，它没有句末可收 —— 只能平直地停下。
把五个这样的片段拼起来，听感就是**五句都被掐断**，无论拼接多干净。

所以修复不在"怎么拼"，而在**送什么进去**。

### 22.4 改动

```go
// softTerminators 不再作为切点
const softTerminators = "，、；：,;:"

// 切点只有句末标点
if isHardTerminator(r) { cut = j; break }   // 。！？
if isSoftTerminator(r) { lastPause = i + 1 } // 只记录，不切
if seen >= max {                              // 整句超长时才退而求其次
    cut = lastPause (若够靠后) 否则 i+1
}
```

同时把在线上限 **15 → 90**（服务真实硬限是 100）：

- 低上限**加剧**了问题 —— 上限越低，段数越多，残句越多
- 实测：41 字回复从 **4 段**变成 **1 段**

**顺带修掉一个真 bug**：`NewSplitterCapped` 原本只在 `maxChunk < 派生值` 时才采用它。
而默认 target=20 的派生值是 **80**，**低于**在线上限 90 ——
于是服务的真实上限被**静默忽略**，200 字的长句可以照样发过去被拒绝。
现在 cap 直接生效，只有安全上限 `absoluteMaxChunkRunes` 在其之上。

### 22.5 效果

```
synth [31字] 今天是十月二十四日星期五，你一共有五件待办，其中两件今天到期。  ← 完整句子
synth [23字] 上午的复习计划还没有开始，下午三点有一个会议。                 ← 完整句子
REVEAL (54 字)
PLAY ×2
```

**5 段残句 → 2 段完整句子**，与用户选中的"更正常"版本一致。

### 22.6 测试改动（删掉了固化 bug 的断言）

两个测试**原本在断言错误的行为**，必须改：

| 原测试 | 原来断言 | 现在 |
|---|---|---|
| `TestSplitterSplitsLongClauseOnComma` | 逗号必须切分 | **删除**，改为 `TestSplitterDoesNotSplitAtCommas` |
| `TestOnlineChunksBreakAtPunctuation` | 按逗号切出多段 | 改为 `TestWholeSentencesAreNotSplit`（断言只在句号断） |
| `TestChunkCapOnlyLowersTheBound` | cap 只能收紧 | `TestChunkCapIsClampedToTheSafetyCeiling`（cap 直接生效） |
| `TestNoticeSpokenInFull` | 靠 6 字 target 切出多段 | 改为断言通知整句完整 |

> **`.dev/check-frontend.cjs` 的 §16 也整段重写了。** 它原来写着
> "reaching the cap backs up to the last punctuation"，把切逗号当作**正确行为**来守护 ——
> 静态检查**固化了 bug**，所以代码改对了它反而报错。
> 这类检查的价值完全取决于它编码的是不是**正确的意图**。

### 22.7 我这一轮的流程错误

回头看，正确的顺序应该是：

1. 用户报告"断掉"
2. **把候选解释都列出来**（静音 / 切点位置 / 残句 / 播放层）
3. 对每个解释设计一个**能证伪**的实验
4. 让用户听 A/B 定案

我实际做的是：先认定"长度"，实现，然后才测量 —— 而测量**三次都没支持**这个认定，
**我却仍然保留了这个改动**，理由是"便宜可逆"。这不是理由：
一个错误的改动**改变了用户听到的东西**，而且**掩盖了真正的病因** ——
低上限让残句**更多**，等于把问题放大了。

> 教训：**"便宜可逆"不能代替"先验证"**。当测量和自己的假设冲突时，
> 要么找到能证伪的实验，要么**把选择权交给能直接感知的人**（这里是用户的耳朵），
> 而不是挑一个"代价小"的方向继续走。
