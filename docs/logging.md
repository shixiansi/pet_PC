# 日志

> 用户可见的行为在 [README](../README.md) 的「日志」一节。这一页写的是**为什么这样设计**、
> 格式的契约，以及加功能时要在哪儿补一行。

## 1. 为什么有这一层

2026-10 之前只有 `App.DebugLog`：它只在 `PETPC_DEBUG=1` 时打开 `debug.log`，写一行
`15:04:05.000 消息`，没有等级，也没有任何界面能读它。

结果是三类问题全都无法回答：

| 报告 | 当时能拿到的证据 |
| --- | --- |
| 「插件点了没反应」 | 无。插件的帧在沙箱 iframe 里，宿主在另一个进程，`log.Printf` 在 Windows 上通往虚空 |
| 「模型不回话」 | 无。端点、模型、密钥都住在**插件**的设置里，请求却由**宿主**发出，两边都没留痕 |
| 「能给我看一下日志吗」 | 得先让用户重新启动一次程序，而且他还不一定肯 |

这一层（`internal/logging`）换掉的就是这三件事：**一直在写、有等级、有一个界面能读**。

## 2. 两个程序，两个文件

```
<dataDir>\logs\pet.log       桌宠写
<dataDir>\logs\market.log    控制中心写
<dataDir>\logs\*.log.1       上一代（轮转产生）
```

**为什么不合成一个文件。** 两个进程追加同一个文件，轮转就没法安全地做（各自 rename 一个对方
还开着的文件）；而「合并成一个日志」这件事，用户真正想要的是**一份按时间排的视图**，那由
`logging.Read` 在读取时做（见 `logapi.go` 的 `LogTail`），而不是由两个写者去抢同一把锁。

`internal/logging.Read` 是唯一的读者，它把两个文件（含 `.1`）按时间戳归并。所以「对话插件
不说话」的答案在**桌宠那一半**，而用户面前的窗口属于控制中心——两边必须并起来看。

## 3. 行格式（契约）

```
2026-10-28T14:32:00.123+08:00 INFO plugin com.shixiansi.plugin-chat llm.chat ok（payload 84 B → 196 B，in 812ms）
└─ 本地时间 + 偏移          └ 等级 └ 子系统 └ 插件（或 "-"）        └ 正文（一行，不折行）
```

- 单一空格分隔的五个字段，`Entry.Line()` 与 `Line` 的逆函数 `ParseLine` 在同一个包里，
  **写与读不可能各说一套**（`TestLineRoundTrips` 守着）。
- 时间带偏移：`09:05 提醒响了` 这句话离开时区就没有意义，而从读文件那台机器反推时区正是
  「默认一切都是 UTC」那类 bug 的另一种写法。
- 正文里的换行会被压成 `" / "`。这不是洁癖：一条能带 `\n` 的消息可以让**别人**写出一行看起来
  像宿主自己写的日志（`TestNewlinesInAMessageCannotForgeAnEntry`）。
- 单条正文上限 4000 字节，超出按 rune 截断并注明——一行日志不该把页面的排版撑爆。

## 4. 等级

| 等级 | 什么时候用 | 例子 |
| --- | --- | --- |
| `DEBUG` | 排查才需要的逐帧细节 | **插件读写自己的数据**（`storage.*`/`share.*`/`config.*`/`memory.*`）、每次模型 POST/状态码/重试、页面报上来的指针事件、调用字节数 |
| `INFO` | 程序的故事 | 启动、托盘、快捷键登记、**插件做了什么**（气泡/浮层/音频/模型/网络/进程/订阅）、每轮模型往返、提醒弹出 |
| `WARN` | 没成功但程序活着 | 闸门拒绝（未授权/未启用）、模型 401/超时、重试过、裁剪失败 |
| `ERROR` | 用户会看见的失败 | 托盘装不上、窗口区域设置失败、页面报上来的错误 |

默认 `INFO`。这一档的选择就是这次改动的目的：**用户报错时已经有一份证据**，而不是让他先去设
一个环境变量再复现一次。

降级到 `DEBUG` 的开关：`PETPC_LOG_LEVEL=debug|info|warn|error`（优先），或旧的
`PETPC_DEBUG=1`（等价 debug）。两个程序读同一套变量（`logLevelFromEnv`，各自四行——
两个程序没有共享的「这个安装怎么配置」的家，多一个只被别人 import 的文件不值得）。

## 4.5 重复合并（`Throttle`）

一条铁律"一次插件调用一行"在真机上直接翻车：插件会**轮询**。实测一份日志里 9729 行
`share.get`、2842 行 `storage.get`、580 行 `config.get`，对 32 行 `llm.chat`——**99.5% 是插件
在读自己的文件**，用户点开日志页只看到一片 `storage.get ok（payload 14 B → 30 B，in 1ms）`。

两件事一起修：

1. **等级由方法决定**（`internal/plugins.DataMethod`，两个宿主共用）：数据面
   （`storage.*`/`share.*`/`config.*`/`memory.*`）记 `DEBUG`，动作面（气泡/浮层/音频/模型/网络/
   进程/订阅）记 `INFO`，失败一律 `WARN`。轮询既可能读也可能写，所以只靠等级不够——
2. **同一 `(插件, 方法, 等级)` 5 秒内只写一行**（`logging.Throttle`），被吞掉的次数附在下一行上
   （`同类另有 37 次已合并`）。这一条保住了"它还在动"这个信号：只写一次然后永远沉默，看起来
   就是卡死。

窗口 5 秒是按肇事流量定的：每秒一次轮询 → 每 5 秒一行（仍看得出在跑）；而真正的动作（弹气泡、
调模型、装插件）间隔远大于 5 秒，不会被合并。合并发生在**写文件之前**，所以 `DEBUG` 也不会被
轮询灌满。
## 5. 保留

- 单文件上限 `DefaultMaxBytes` = 2 MB，超过就把 `pet.log` 改名为 `pet.log.1` 再重开。
- **只有一代**，所以每个程序最多约 4 MB。这不是可配置项：一个说不清失败场景的旋钮只会
  变成支持问题。
- 每次写都是「打开 —— 追加 —— 关闭」，**不在两行之间持有文件**。三个理由，而且第一个是
  被测试撞出来的（`Market` 的每个用例都在 `TempDir` 清理时失败）：
  1. Windows 上**改名一个被打开的文件会失败**，于是轮转静默退化成截断，「保留上一代」这个
     承诺是假的；
  2. 控制中心（另一个进程）要读这个文件，用户也可能在记事本里打开它——一个常开的写句柄会让
     两者都失败；
  3. 退出时没有东西要 flush，硬杀也不会留下半行。

## 6. 里面不许有什么

**对话正文、待办内容、插件设置的值、任何密钥。**

记的是「谁调了什么、花了多久、结果如何」：方法名、插件 id、字节数、条数、tokens、耗时、
错误文案。这条不是风格偏好——日志是给 issue 贴的，而控制中心「高级 → 生成诊断报告」直接
复制它。一处 `log.Debug("llm", payload)` 就能让每一份报告都不能外发。

守它的测试：

- `internal/llm/log_test.go` —— 传输层的每一行都不含用户的话、密钥、服务端返回体；
- `app_log_test.go` —— `llm.chat` 与每次插件调用都不含 payload 与回复正文；
- `tools/plugin-market/logapi_test.go` —— 页面读到的是文件里真有的东西。

## 7. 加一行日志要改哪儿

| 位置 | 补什么 |
| --- | --- |
| 新的插件能力（`app_plugins.go` 的 `pluginMethods`） | 什么都不用加：`PluginRequest` 已经为**每一次**调用写了一行（方法、结果、耗时、字节数） |
| 宿主自己的子系统 | `a.log.Info/Warn/Errorf("子系统", …)`；子系统名就是日志页的筛选项，别随手造同义词 |
| 插件自己的关键动作（模型、工具） | `a.log.Pluginf(level, "llm", id, …)`，插件 id 单独一列，页面按它筛 |
| 跨进程的界面（控制中心） | `m.log.*`（写 `market.log`）；要给用户看的用 `LogTail` 那个绑定，不要另开一条通道 |
| 页面（webview）里捕获到的错误 | `App.PageLog('error', message)`，和 toast 同一句——toast 只活 3.2 秒 |

## 8. 这一层的边界

- **它不是指标系统**：没有计数器、没有上报、没有遥测（README「明确不做」）。
- **它不重试、不缓冲、不阻塞**：写失败就记在 `Logger.err` 里，之后继续尝试；一条日志绝不让
  主路径失败。
- **它不替测试做人**：`newTestApp` 构造的 `App` 没有 logger，所有方法对 nil 接收者安全——
  这是刻意的，否则八十个调用点各写一次 `if a.log != nil`，总有一个会漏，而漏掉的那个正好在
  已经出错的路径上。
