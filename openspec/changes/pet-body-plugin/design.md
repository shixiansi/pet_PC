# design: 宠物本体也拆成插件

## 1. 为什么是"一个帧",而不是"插件给一张图"

两条路都能让宠物换脸：

| 路 | 形状 | 代价 |
| --- | --- | --- |
| A. 插件提供**图片**（`storage` 里一张 png / svg，宿主 `<img>` 它的地址） | 宿主仍然是画宠物的人 | 动画、表情、随状态变化、按等级换装全都进不来；宿主还得学会"宠物图怎么随时间变" |
| B. 插件提供**文档**（沙箱 iframe，整格铺在宠物那一格） | 宿主只管矩形与裁剪 | 一个额外的 iframe，和浮层面/常驻帧同一套机制 |

B 是唯一和现有结构一致的答案：`plugin-host.js` 已经是"在宿主算好的矩形里挂一个插件文档"的
实现，`#pet` 的矩形本来就是布局的一部分、也本来就在窗口区域里。选 A 等于让宿主继续认识
"宠物长什么样"，而这正是这次要拆掉的东西。

## 2. 为什么不新增权限

`AllowedPermissions` 的规矩是**每一项权限背后至少有一个方法**（`TestCapabilityTableIsComplete`）。
`body` 没有方法可挂：它不是一个插件主动"打开"的东西，而是"装好 + 启用 + 授权之后它就是那只宠物"。
于是它走 `background` 那条老路：**manifest 字段 + 既有权限门控**。

门控选 `pet.surface` 而不是新词，理由是**用户被问的是同一件事**：
"这个插件会在桌宠身上画东西"。`pet.badge`（头顶一行字）已经挂在这一项下面，浮层面也是。
把一个插件在宠物身上画画拆成三种授权，只会让人在第三个对话框里点"允许"而不读。

文案因此改了：`PermissionLabels[pet.surface]` 从"在桌宠旁显示自定义浮层面"变成
"在桌宠身上或旁边显示你自己的界面（浮层面、头顶的一行字、宠物本体）"。

## 3. 为什么这一层必须 `pointer-events: none`

宠物身上的手势是**宿主的**，而且每一条都有用户已经学会的含义：

| 手势 | 现在做什么 | 如果本体帧吃掉指针 |
| --- | --- | --- |
| 按住拖 | 移动窗口（`StartDrag` / `DragTo`） | 宠物拖不走 |
| 右键 | 打开九宫格菜单（`BubbleMenu`） | 右键没反应 |
| 悬停 | 浮出对话按钮 | 按钮浮不出来（`#pet:hover` 不再触发） |
| 单击 | 有意为之的空动作 | —— |

一个"能点的宠物"最自然的实现是本体的 DOM 接事件，但那会让上面四条全部失效——而它们不是
装饰，是这台程序唯一的入口。所以边界划在"插件画、宿主收手势"：想放可点的东西，用浮层面
（`surface`）或气泡（`pet.bubble`）。这条也写进了插件手册，因为它是**作者最容易做错的地方**。

## 4. 几何：为什么告诉它尺寸，但不给它位置

帧由 CSS 铺满 `#pet`（`position: absolute; inset: 0`），位置永远不需要算。但插件**必须**知道
自己多大：宠物尺寸是用户的设置（`petScale`，0.5×–3×），一个假设 150×200 的本体在 1.5× 下会
把自己的脚画到框外——而框外就是窗口区域之外，Windows 直接切掉。

所以 `init.surface.rect` 带 `{x:0, y:0, w, h}`，尺寸变化时再发一条 `surface`（和浮层面同一套
机制、同一个消息类型）。`rectIndex` / `rectCount` 恒为 0/1：本体只有一格。

## 5. 为什么"同一时间只有一个",以及谁赢

一个宠物只有一张脸，「我的宠物左半边是你的、右半边是它的」不是用户能解决的冲突。规则：

- 清单顺序（`plugins.json` 的安装顺序）里第一个满足 **已装 + 已启用 + 仍持有 `pet.surface`**
  的插件赢；
- 页面在 console 里点名其余声明者（一次安装只打一次，不会刷）；
- 它消失（卸载 / 停用 / 撤权 / 换版本）时，帧销毁、自带图片回来——这条由 1.5 秒的
  installed 轮询驱动，不需要重启。

**为什么"撤权"也要算进来**：`init` 里带的是挂载那一刻的 `granted`，插件据此决定自己画什么。
用户事后取消授权而帧还活着，就是让一个没被授权的文档继续在宠物身上画画。所以 `granted`
是重建键的一部分（和 `background` / `surface` 同一套理由，见 `plugin-host.js` 的 `surfaceGranted`）。

## 6. 回退：`<img>` 不销毁，只是不显示

卸载本体插件之后要立刻看到那张图，而重新 `<img src>` 一次意味着重新解码（`renderPet` 里
那段"只在 src 真的变了才赋值"的注释就是为这个闪一下写的）。所以图一直在文档里，
`#pet.body-from-plugin #pet-image { visibility: hidden }` 只是不画它。

## 7. 与既有机制的关系

| 机制 | 本体帧的行为 | 为什么 |
| --- | --- | --- |
| `event` 投递 | 投（`routeEvent`） | 它是常驻的，"提醒来了宠物抖一下"是本体最自然的用途 |
| `theme` | 投（`setTheme`） | 帧里有自己的文档与配色 |
| `plugin.call` | 能回答（`frameForCall` 里排在常驻帧之后） | 它和常驻帧一样一直挂着；一个画宠物的插件被问"你现在什么样"是合理的 |
| 几何 | `placeBody` 发 `surface` | 和浮层面同一套消息 |
| 沙箱 | 同一个 `PluginFrame`（`allow-scripts`，无 `allow-same-origin`） | 它就是插件文档，没有第二种 |
| 区域裁剪 | 不改 | 宠物矩形本来就在区域里 |

## 8. 被否决的方案

- **把 `pet.badge` / 角标也交给本体插件**：那会让番茄钟与待办依赖"用户装了一个会画宠物的插件"。
  现在它们是两个**宿主能力**，与"宠物长什么样"分开；这次不动。
- **给本体帧开放指针事件**：见 §3。
- **本体插件也走 `surface`（把宠物当成一块浮层面）**：区域裁剪的语义完全不同——浮层面是
  "宠物旁边那块槽位，同一时间只能有一个"，而宠物本体是**永远在**的那一格。混用会让
  "气泡/浮层面/本体"三者的可见性规则互相打架。
