# design: 插件页挂载每个插件的界面

## 1. 三个决定

| 决定 | 备选 | 为什么 |
|---|---|---|
| `plugin.share` 由两个宿主共同服务 | 继续只由桌宠服务，插件页不挂浮层面插件 | 「谁可以读谁的键」是 manifest 的规则，不是宠物的能力；文件在 `plugin-data/<id>/share/`，控制中心同样拥有那棵树。上一轮的"不挂"把三个插件的界面藏起来了，而它们恰恰是唯一需要界面的三个 |
| 文档靠 `surface.slot` 判断自己在哪个窗口 | 新加一个协议字段（`init.host`）、或按 URL 参数区隔 | `slot` 已经是宿主对"你是哪一个外观"的既有词汇：桌宠给 `chat`/`todos`/`pomodoro`/`background`，控制中心给 `workshop`。一个新字段会让两边的 `init` 再分叉一次，而 URL 参数是另一条通道（`theme` 用它是因为它要先于首帧生效） |
| 对话在控制中心**只读** | 把 `llm.chat` 在控制中心实现一份 | 见 §4 |

## 2. `surface` 为什么不再是拒绝理由

上一轮的判断是："浮层面的矩形是从**宠物**的角量出来的，这个窗口没有宠物，所以不挂。"

前半句是真的，后半句是错的：矩形是宿主的事，文档根本不需要知道宠物的坐标——它只知道自己
被塞进了一块区域（`body` 的 100%），并且在 `init.surface` 里被告知"你是哪个外观"。真正的
事故（`share.set` 不支持）与矩形毫无关系，是**能力表缺了一项**。

所以规则改成"已装 + 已启用 + 有 entry"，而缺的能力按文档自己的能力降级：

| 插件 | 在 `workshop` 里缺什么 | 它怎么表现 |
|---|---|---|
| 待办 | 无（`storage`+`share` 都服务） | 完整列表，可写 |
| 番茄钟 | `share` 里的 `command` 没人读（计时帧在桌宠） | 隐藏倒计时按钮，写明"计时在桌宠上"；记录照读 |
| 对话 | `llm.chat` | 输入框只读 + 状态行写明发送在桌宠旁 |
| 语音 / QQ / B站 | 无（它们本来就只为这个窗口写） | 不变 |

## 3. 待办页删除，而不是改成"读插件的存储"

控制中心读插件的私有目录是可以做到的（`storage` 那一套就在这个程序里），但那会造出**同一份
列表的第二个渲染器**：字段、排序、空状态、勾选语义都要再写一遍，并且和插件自己的列表必然
分叉（这就是"旧待办页读 `todos.json`"的翻版，只是换了个文件）。列表的界面只有一个实现——
插件自己的文档——两个程序都挂它。

顺带删掉 `Market.Todos()`：一个没人调用但还在的能力，早晚被人当成"这个程序能读待办"。
`DataDir()` 留着——那是设置页要展示的路径，不是别人的数据。

## 4. 为什么对话在控制中心是只读的

三条路摆过（用户确认选中间那条）：

1. **在控制中心实现 `llm.chat`**：要搬凭据解析（自己的 + `llm.borrow` 借别人的）、每日预算计数、
   `plugin-data/<id>/llm-usage` 的写入、流式帧的事件下行，还要与桌宠**同写**一个用量文件——
   那正是本仓库「一个文件只有一个写者」要避免的东西，也是上一轮"市场程序不 import
   `internal/llm`"这条决定的反面。代价远大于收益。
2. **只读历史**：`storage` 就够（历史本来就在插件自己的键里），输入框禁用并写明原因。用户
   在控制中心看到完整往来，发送仍在桌宠旁那块浮层面里——那里本来就有一个可用的输入条。
3. **不挂**：等于把"没有界面"这条抱怨原样留着。

选 2。它的实现成本是插件里的一条 `workshop` 分支（`canChat = granted.has(PERM_CHAT) && !workshop`
+ 一句状态文案），桌宠那边的路径一行未动。

## 5. 番茄钟：设置靠声明，记录靠读

- **设置**：`machine.js` 的 `phaseMinutes` / `longBreakEvery` / `autoStartNextPhase` 早就在读
  `cfg.*`，只是 manifest 没有声明——于是「设置」这个控件没有出现的理由。补声明之后：
  - 默认值必须与 `machine.js` 的兜底**逐字一致**（25 / 5 / 15 / 4 / true），否则升级那一刻会
    把正在用的人的专注时长改掉；
  - 只声明**真的被读**的键。这一轮差点写进一个 `soundEnabled`（"结束时响一声"）——它没有实现，
    也没有 `audio` 权限，删掉了。声明一个什么都不做的开关正是本仓库明令禁止的那类缺陷。
- **记录**：`pomodoro-records-v2` 一直由计时帧写、没人读。现在视图（桌宠的浮层面、控制中心的
  页面）都读它：
  - 只读——第二个写者就是 read-modify-write 丢记录，这个文档的注释里写着；
  - 视图每 5 秒重读一次（不是每秒：记录只在一段结束时变，而状态是每秒变的）；
  - 新在前、最多 20 行、`summary` 为空就不占位（"跳过"是正常操作）。

## 6. 待办的轮询

列表角色以前只在挂载时读一次（"浮层面是唯一的写者"）。现在同一个列表可以同时开在两个窗口，
一次读会让另一边的改动看不见。所以：

- 每 2 秒重读；
- **写请求在飞时暂停轮询**：一次在写之前发出的读，若在写之后到达，会把旧列表盖回屏幕上。
  实现是 `writes` 这个 id 集合——`storage.set` 的 id 记进去，响应到达时删掉，轮询看它是否为空。

不选"让另一个窗口刷新"：那需要一条跨窗口通知，而两个窗口属于**不同的进程**。

## 7. 已知取舍

- **控制中心显示的计时是"最后持久化的状态"**：没有计时帧在跑，倒计时不会走。所以那里隐藏了
  按钮，而不是显示一排点了没反应的控件。
- **待办的写入仍是"最后写入者赢"**：两个窗口同时改同一行时，后写的覆盖先写的。风险与以前
  "两个浮层面实例"相同（宿主每个插件只挂一个浮层面，但控制中心是第二个宿主），没有引入新的
  存储机制——真正的修法在 `storage` 那一层做版本号，那是另一个 change。
- **`share` 的实现从桌宠搬到 `internal/plugins`**：桌宠的三个方法名保留（能力表与既有测试都
  指着它们），只是变成转发。搬迁不改变任何字节语义（`share/` 目录、`share-` 前缀的旧文件、
  64 KiB 上限、`shareRead` 校验都原样）。
