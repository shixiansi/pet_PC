# design: 模型渠道

## 1. 为什么"插件之间不互相调用"仍然是前提

这一版**没有**让记忆核心去调对话插件，也没有让谁去调"模型管理插件"。所有取用都经过宿主：

```
插件 ──llm.chat {provider?}──▶ 宿主（解析端点与密钥、计数、发请求、流式回推）──▶ 服务商
```

宿主知道"谁的配置"，插件只知道"用了谁、哪个模型"。这条边界从 `llm.borrow` 第一天就是这样，
本次只增加了**点名**与**清单**。

## 2. `provider` 为什么是"插件 id"

PetPC 里没有路由注册表，也没有第二个唯一标识：插件 id 已经是（a）唯一、（b）用户在安装/设置界面
看得到、（c）manifest 里能写死的东西。把渠道名做成"插件自报的路由名"会引入一个新字段（manifest
变更要走七处同步）而收益只是换个拼写。

代价写在这里：一个插件只能提供一个端点（`llmBaseUrl` 是单值）。要多渠道就多装几个——这反而让
"哪个账号在花钱"在界面上是分开的，比在一个插件里塞 N 个渠道更难骗自己。

## 3. 解析顺序（`resolvePluginChatCredential`）

| 情况 | 结果 |
| --- | --- |
| `provider` 非空，等于调用方自己 | 拒绝："渠道要由别的插件提供" |
| `provider` 非空，调用方没有 `llm.borrow` | 拒绝，并点名权限 |
| `provider` 非空，被点名的不是就绪借出方 | 拒绝，并点名那个 id 与它缺什么（**不回退**） |
| `provider` 非空，就绪 | 用它 |
| `provider` 为空，自己配置齐全 | 用自己的（保留"填了自己的就不借"这条退路） |
| `provider` 为空，自己没配 | 借 id 最小的就绪借出方（老规则，不变） |

`findLLMLender(exclude, only)` 里 `only` 与 `exclude` 走同一个谓词（`pluginOwnChatCredential` 的
ready），所以"被点名的渠道"和"默认选中的渠道"不会有一方更宽松。

## 4. `llm.providers` 的形状与边界

```jsonc
{ "providers": [{"id","name","model","ready","self"}],
  "default": "<不点名时会用的那个 id，可能为空>",
  "own": {"ready", "model"} }
```

- `self: true` 是调用方自己那一行：列表不藏它，否则调用方的界面会把"自己"显示成一个可借的渠道。
- `ready` 用同一个谓词算出来，因此列在这里 ready 的渠道不会因为"配置不全"而在选中时失败。
- **没有端点、没有密钥**：与 `llm.profile` 同一条线。测试里直接断言输出里不含 stub 的 URL。

## 5. 预算与日志

- 预算仍然按**调用方**计（`readPluginUsage(dir)` 用的是调用方的私有目录）。点名渠道不会让调用方
  绕过自己的每日上限，也不会花借出方的额度——这一点和之前一样，只是现在能选"花在哪个端点上"。
- 借用时那行 INFO 日志（`借用 %s 的模型配置（%s）`）在点名路径上同样会写，所以"这次到底走了哪个
  账号"在 `pet.log` 里查得到。

## 6. 备选方案

| 备选 | 为什么不 |
| --- | --- |
| 让插件注册 provider 适配器（DSH 的 `ctx.llm.registerAdapter` 形状） | PetPC 的插件是沙箱 iframe，注册不进宿主；要做就得给宿主加一套插件可写的运行时，那是另一个量级的机制（而且会绕开"宿主决定能连哪"这条白名单） |
| 用 manifest 字段声明"我能用哪些渠道"（像 `callTargets` 那样精确） | 渠道是**用户**配的，不是作者写死的；换渠道不该需要插件升级。而且精确清单会让"用户新装一个渠道"变成"其它插件全部要更新" |
| 加一项 `llm.channels` 权限 | 一个没有独立方法族、只是"同一类同意里选一个"的开关，正是这份词表存在的要防的东西。两次修订（`timer.*`、`todos.*`）已经把这条边界试过一次 |
