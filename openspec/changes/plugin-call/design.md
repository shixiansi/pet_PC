# design: plugin.call —— 决策、形状与代价

## 1. 一条无法绕开的约束：Go 不能向插件提问

Wails v2 给 Go 的只有一个方向：`runtime.EventsEmit`（发完就不管），以及被 JS 主动调用的
绑定方法。**没有**"Go 调用页面并等一个返回值"的通道。

插件帧的答案只存在于页面里，所以：

> **授权在 Go，送达在页面。** 方法是两阶段的，而不是一次调用。

这不是为了省事，而是唯一能同时保住"闸门在 Go"和"答案是插件给的"的形状。

### 阶段 A —— Go：只发信封，不做任何事

`plugin.call` 在 `pluginMethods` 里就是一条普通方法，于是它免费继承了 `PluginRequest` 的
全部性质：一条 INFO 日志、失败 WARN、5 秒去重、以及那条不可动摇的检查顺序。

`Run` 只做校验，返回一个**授权信封**：

```json
{ "ticket": "9f2c…", "target": "com.example.memory-core",
  "method": "chat", "payload": { … } }
```

按顺序拒绝（任何一步拒绝，什么都没发生——没有帧被触碰，没有字节被投递）：

| # | 条件 | 拒绝时的说法 |
| --- | --- | --- |
| 1 | 调用方已装、已启用、已授予 `plugin.call` | 由 `Dispatch` 给出（不变） |
| 2 | `target` 是合法插件 id，且 **不是自己** | "不能调用自己" |
| 3 | 调用方 `callTargets` 里有精确的 `<target>/<method>` | 点名那一项，与 `share.get` 的措辞一致 |
| 4 | 目标已装、已启用 | "插件 X 未启用" |
| 5 | 目标也授予了 `plugin.call` | "目标没有获得 plugin.call" |
| 6 | 目标 manifest 的 `serves` 里有 `method` | "目标没有声明会回答 method" |
| 7 | payload ≤ 64 KiB | 与 `MaxShareValue` 同一个数量级与同一个理由 |

`ticket` 是 16 字节随机十六进制，Go 不记账。它只用来让页面把"回包"配给"这一次调用"——
带错 ticket 的回包会被丢弃，重放的 ticket 也不会造成第二次投递（页面在发出时就把
ticket 绑到了那一个等待项上，结算即删除）。

### 阶段 B —— 页面：投递、等待、结算

`PluginHost` 是所有帧的主人的这一点没有变，所以投递只有它做得到：

1. 调用方帧的 `dispatch` 走的是 `PluginHost.request(pluginId, method, payload)`（三处
   `onRequest` 都改成它）；`method === 'plugin.call'` 时它先走
   `App.PluginRequest` 拿到信封；
2. 按 id 找目标帧：**常驻（background）帧优先**，其次才是当前浮层面那个插件的帧；
   找不到就立刻以"目标插件的常驻帧没有在运行"失败——这是**投不出去**，不是没权限；
3. 往目标帧发 `{ v:1, type:'call', ticket, from, method, payload }`，等待回包；
4. 目标回 `{ v:1, type:'call-result', ticket, ok:true, result }` 或 `{…, ok:false, error }`；
   回包只接受**来自被问的那个帧的 `contentWindow`**，且 ticket 必须对得上；
5. 结算：`ok` 则把 `result` 当成调用方的返回值（于是调用方拿到的就是普通
   `response.result`），否则以 `error` 拒绝。

`result` 超过 64 KiB 直接拒绝而不是截断：截断的 JSON 在调用方那里会变成一个更难查的
解析错误。

## 2. 上限：深度与超时，都只能放在页面

- **深度 3。** A 调 B 调 C 调 D 就停（`call` 消息里的 `depth` 由宿主写，插件改不了它自己的
  入站信封；被问的一方再发起调用时，宿主会带着它当前的 depth 继续）。没有它，A↔B 互相提问
  就是一个不会报错的死循环，而症状是"两个插件都卡住"。
- **超时 30 秒。** 被问的一方可能在等一次 `llm.chat`，所以它比一次普通能力调用宽得多。
- 两个数字都放在页面，因为 Go 看不到调用链，也无法在等待上计时。两者的失败都不是权限
  决定，所以不违反"前端从不判断权限"。

## 3. 权限模型：一个开关，两侧各一句声明

- 权限 `plugin.call`（第 14 项）：**调用方与被调用方都要有**。用户读到的是一句
  "与其它插件互相调用"；具体到哪一对，靠 manifest 的两张清单念出来。
- `callTargets`（调用方，`<id>/<method>` 精确对子，最多 8 项，与 `shareRead` 同规则：
  合法 id、合法名字、不列自己、不重复、没有通配）。
- `serves`（被调用方，扁平方法名，最多 8 项，同 `configKeyPattern` 形状）。
- 两张表都**要求** `plugin.call`，否则解析即失败——和 `shareRead` 没有 `plugin.share` 就
  拒绝是同一句话：一份没人能兑现的声明比没有声明更坏。

**没有权限转移**，这是最重要的一条：被调用方执行时用的仍是它自己的 `row.Granted`。
所以"接入端 A 借此间接用上了核心插件的模型预算"是**设计事实**而不是漏洞——用户装核心插件时
已经为 `llm.chat` 点过头了；而 A 拿不到那个 key，也调不动核心没声明 `serves` 的任何东西。

## 4. 备选方案与它们被否的原因

| 备选 | 为什么不做 |
| --- | --- |
| 继续用 `plugin.share` 轮询当邮箱 | 往返两次轮询（现成样本是 2 秒档）、一格邮箱、无 ack、无超时；写 WAL 只能把"可能丢"变成"可能重复"。这种靠时间戳对账的桥，仓库里已经有一份（B 站），不该有第二份 |
| 让插件开一个本地 HTTP 端口互相调 | 没有这项能力，而且它会让 `net.fetch` 的域名白名单变成装饰：任何插件都能拨 `127.0.0.1:<任意端口>` |
| 宿主自己做一个"记忆服务" | 那是把人设与记忆搬进宿主，撤销 `AGENTS.md` §1 的决定（宿主不认识任何具体插件） |
| 宿主在 `plugin.share` 上加推送（`share.watch`） | 只解决"通知"，不解决"答案"；请求-响应仍然要靠两格键和一次猜测，而且它会让托盘变成事件总线 |

## 5. 已知代价

1. **多一次跨越。** 一次调用是"帧 → Go → 帧 → Go → 帧"，比进程内函数调用贵得多；这是沙箱的
   定价，不是实现的疏忽。所以核心插件应当**按一次问答**收费，而不是按一条消息里的每一句。
2. **答案在 Go 眼里是不透明的。** 日志里只有"谁问了谁什么"和成败，没有内容——这与
   `llm.chat` 正文只在 DEBUG 记的规则是一致的。
3. **被问的一方必须常驻。** 没有常驻帧的目标只有在它自己的浮层面开着时才答得上；这是
   "无人看着时也能被问"必须用 `background` 换来的，和今天的事件投递同一条规则。
4. **控制中心不支持**（见 proposal 的非目标）。插件在两个窗口里能力不同这件事，手册本来就
   要求"缺的能力要说出口"。

## 6. 第一个用户暴露的一条缺口：常驻帧的门控

写第一个真正的被调用方时撞上的事：**一个"被问"的插件没法申请常驻帧**。

`validateBackground` 原来只认 `events` / `net.ws` / `net.fetch` 三项，理由写得很清楚——常驻帧
的用途是"无人看着时收东西"，所以必须有一项权限说明它收的是什么。而记忆核心三样都不是：
它没有宿主事件要听、没有自己的 socket、也没有轮询表；它的入站流量就是**别的插件的 `call`**。

于是只有两个选择：给它一项它永远不用的权限（用户会被问一个什么也不做的开关——正是这份词表
存在要防的事），或者承认 `plugin.call` 也是"一种收东西的方式"。

选后者：`plugin.call` 是一条**别人推给我**的通路，和 `net.ws` 同一类（只是对方是插件而不是
服务），所以它同样能说明"这个常驻帧是干什么用的"。这条改动落在
`internal/plugins/manifest.go` 的 `validateBackground`，README 与手册的 `background` 行，
以及自检工具 `plugin-check.mjs` 的同一条规则上——四处，一起改。

## 7. 第一个用户：记忆核心与接入端（住在插件仓）

| 插件 | 角色 | 它声明的 |
| --- | --- | --- |
| `com.shixiansi.plugin-memcore` | 人设 L0 + 分层记忆 L1–L4 + 双链，常驻 | `serves: ["chat"]`，`plugin.call` `llm.chat` `llm.borrow` `storage` `plugin.config` |
| `com.shixiansi.plugin-onebot` | OneBot v11 薄接入端（正向 WS） | `callTargets: ["com.shixiansi.plugin-memcore/chat"]`，`net.ws` `plugin.call` `storage` `plugin.config` |

这两件事在实现时被验证过，值得记下来：

1. **一次调用里可以有一次 `llm.chat`。** 30 秒的超时是给"被问的一方可能正在等模型"留的；
   记忆核心因此把回复默认压在 240 字（更长的回答更容易把这条链路撑爆），并把摘要/画像这类
   额外请求排在回答**之后**（`setTimeout(0)`），不让用户在等它们。
2. **隔离是"没读过"，不是"过滤过"。** 生成只读当前 `roleId` 的角色链与四层记忆；全局事件链
   只写不读。所以两个接入端的记忆不会互相污染，这件事在结构上成立，不依赖任何过滤规则。

两边的测试在插件仓（`market/tests/`）：`plugin-memcore.test.js` 驱动核心的问答与晋升，
`plugin-onebot-memcore-pair.test.js` 把**两个插件装进两个独立的 window**，用一个假宿主按
manifest 的声明转发 `plugin.call`，断言"一帧 OneBot JSON → 群里一句回答"整条链路成立，
并且记忆只落在核心的私有存储里。

### 7.1 真正跑起来的那一个：QQ 端（Milky）

OneBot 适配器写完之后才发现用户手上没有 OneBot 协议端，跑的一直是 Milky。于是同一个原语又接到
**已有的 QQ 插件**上，而它教给我们三件设计上的事：

1. **"换大脑"必须是一条早退，而不是把老路径改造成两用。** QQ 插件的回答路径里缠着能量、表情、
   围栏协议、防拦截阶梯；把核心塞进去会同时动到这些。做法是在 `takeTurn` 最前面加一条
   `if (coreEnabled()) { await takeTurnViaCore(...); return; }`，老路径一行未改——184 个既有
   用例因此全部保持绿，而新路径是一个可以单独测试的新文件（`lib/memcore.js`）。
2. **能力是要还的，而且得付在明处。** 核心只给一句话，而 QQ 插件的主动开口/攒批插话要靠结构化
   回复里的 `silent` 与表情选择才成立，所以核心模式下它们**停下**（日志里写明原因），图片也过不了
   `plugin.call`（它是 JSON，不是多模态），于是把"这条带了 N 张图"如实告诉核心。这些代价写在
   插件页上，而不是留给用户去猜。
3. **开关不一定能放进 config。** 宿主的 `maxConfigItems` 是 40，QQ 插件已经用满。为了一个开关去挪
   宿主的规则是本末倒置，所以开关住在插件自己的 `state/core` 里，跟着既有的 10 秒 `config.get`
   轮询一起重读。**代价是"拨了开关最多 10 秒才生效"**——与宿主那条"改完立刻生效"的约定相比是退让，
   所以它必须写在文档里（README §4.6 与插件页都有）。

配套地，核心多了一个 `seed` 方法：把插件攒下的群记忆一次性导入 L3/L2。没有它，"打开开关"这件事
会让旧记忆变成没人再读的文件——数据没丢，但用户看到的是"它把我记得的事忘了"。

### 7.2 一条规则，两份清单：`validateBackground` 的第四个权限漏了一半

`plugin.call` 加进 `validateBackground` 之后，真机上第一次调用打出来的是：

```
plugin.call ok（payload 146 B → 190 B，in 3ms）              ← 闸门点头了
plugin.call 问不到 com.shixiansi.plugin-memcore：它此刻没有常驻帧   ← 但对面没人
```

原因是"哪些权限能撑起一个常驻帧"这句话在代码里有**两份**：Go 侧的 `validateBackground`（管 manifest
能不能过）与 `frontend/src/main.js` 的 `backgroundPlugins()`（管页面挂不挂那个 iframe）。前者学会了
`plugin.call`，后者还停在原来三项，于是被问的那一端永远没有帧——而**闸门是同意的**，所以日志前半截
看起来完全正常。

这条教训比它本身重要：一份"哪些权限"的清单出现在两个语言里时，**新增一项就是两处**；漏掉的那一处
症状会伪装成"投递失败"，而不是"配置错了"。所以 `.dev/check-frontend.cjs` 现在同时断言两份清单都点名
`plugin.call`——下一次再有人给这一族加权限，静态检查会先红。

同一轮还修了两个由此暴露的小问题：插件页上的「导入」按钮在控制中心里点了必然失败（那里不服务
`plugin.call`），改成常驻帧在开关打开时自动导入一次；导入**全部失败时不盖章**（否则"试过了"被当成
"导成功了"，用户只有手动拨开关才会重试），并给盖章加了版本号，好让旧版本留下的错章自动作废。

### 7.3 被拒的调用会留下 WARN，所以"问了再兜底"不是安静的做法

核心的插件页每 5 秒问一次 `llm.profile`，而控制中心不服务它。插件写了 `catch`、界面照常显示，
但宿主那侧每一次都记了一条：

```
WARN plugin com.shixiansi.plugin-memcore: llm.profile 没有执行 … 本程序不支持该方法
```

于是市场日志被刷成每 5 秒一条。**这就是"插件的 catch 只让界面好看，不让日志安静"**——闸门在拒绝时
就已经记了账，而日志是用户排查时唯一会读的东西。

所以规矩是：**在两个宿主里都可能被挂载的插件，必须按 `init.surface.slot` 预先判断，而不是"问了再兜底"。**
`workshop` 里不存在的调用就不要发（`llm.*`、`plugin.call`、`bubble.say`、`surface.*`、`ws.*`、
`process.*`），界面上写一句"这件事在桌宠那边"即可。B 站插件是这条规矩的旧例：它每个会话只探一次
`llm.profile`，所以只留一条 WARN——可以接受，但同样的 slot 判断能把它也变成零。
