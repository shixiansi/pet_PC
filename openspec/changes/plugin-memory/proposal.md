# proposal: 插件的长期记忆

## 现状

插件可以让模型调用工具（`app_plugin_tools.go`），但**什么也记不住**：
`storage.get/set` 存的是 JSON 键值，是插件自己用的；模型看不见，也不会去维护它。
所以每一次对话都从零开始，"上次说的那个项目"永远得重新解释。

## 方案

一个 markdown 文件，住在插件自己的私有目录里，**由模型通过工具维护**：

| 方法 | 工具名 | 做什么 |
| --- | --- | --- |
| `memory.read` | `memory_read` | 返回整份文档（没有就是空串） |
| `memory.append` | `memory_append` | 追加一条，返回整份文档 |

插件方法让插件自己也能读写（比如让用户在面板里看）；工具让模型能读写。

## 三条硬规则

1. **只追加，不覆盖。** 能重写这份文件的模型能删掉用户依赖的事实，而且是静默的。
   追加一条更正（"其实是 Y 了"）永远可行，且不会丢掉原来那条。
2. **每次改动留一个版本。** 模型一定会写错东西。用户要能看到改了什么、什么时候改的，
   并且能放回去。快照在写入**之前**拍——已经包含错误的那一版没人想要。
3. **有上限（8 KiB / 单条 500 字 / 保留 20 版）。** 这份文件是要在每次对话里读的，
   无上限的积累最终比对话本身还占上下文，而第一个症状是模型对着一墙陈旧的笔记回话。
   满了是**拒绝**，不是悄悄丢掉最旧的一条。

## 为什么不需要第 18 项权限

"我在自己的目录里放笔记"正是 `storage` 已经说过的话。再加一项，用户会面对两个都读作
"在你的私有目录里保存数据"的开关，而他说不出区别——那正是这份清单要避免的东西。

## 非目标

- 向量库 / 语义检索（那是"哪条旧消息提到过这个"，另一个问题，另一个账单）
- 宿主自动把记忆拼进 system prompt。**插件**在自己的提示里告诉模型"先读记忆"，
  因为措辞是插件的事，宿主只提供机制——与工具调用的分工一致。
- 跨插件共享记忆（那是一次跨插件读取，需要它自己的权限与对话框）
