# proposal: 一份自包含的插件开发手册

## 要解决什么

用户的原话：

> 我需要你整理一份插件开发说明，可以由完全独立的模型独立的会话，只通过阅读文档不需要获取
> 宠物本地代码就能开发插件的说明文档。

现状是**契约散落在实现里**，而且只能靠读代码才能拼出来：

| 要写一个插件，必须知道 | 之前只能从哪儿得到 |
| --- | --- |
| manifest 每个字段与它的校验正则 | `internal/plugins/manifest.go` 的 300 行校验 |
| 桥接协议的每条消息与它的 `v:1` 约定 | `frontend/src/plugin-host.js` 与 `cc/src/lib/plugin-frame.ts`（两份） |
| 13 项权限各自 gates 哪些方法 | `capability.go` + 两张能力表 |
| 34 个方法的 payload/返回/上限 | 散在 `app_plugins.go`、`privatestore.go`、`plugins/share.go`、`internal/plugins/memory.go` 里 |
| 浮层面的几何语义（`anchor`/`maxH`/`blocks`/`tailX`/`room`） | `app_plugin_surface.go` 的注释与 `manifest.go` 的 `Rect` |
| 哪些数据不属于你（待办、番茄钟的记录） | 几个 change 的设计文档 |
| 怎么在没有宿主的情况下自检 | 没有：只能装到真机上试 |

外部的模型（或一个刚加入的人）拿不到这些，写出来的插件会踩三类必然的坑：
协议的第一条消息就错（`init` 被守卫丢掉）、把浮层面的矩形当成 CSS 自动高度、
把别家插件的数据当成宿主的能力。

## 做什么

写 `docs/plugin-dev.md`（约 1050 行 / 50 KB，中文），**自包含**：

1. **运行模型**：宿主 / 沙箱 iframe / 桥 / 闸门，以及"同一个插件可能同时有 4 种挂载、
   互不共享内存"这条决定设计的事实；
2. **一个能跑的最小插件**（`manifest.json` + `panel.html` + `app.js` + `style.css` 全文），
   含一段 40 行的桥接客户端——**它可以被逐字复制**；
3. **本地开发与手工安装**：数据目录、`plugins/<id>/`、`plugins.json` 的条目形状——
   不需要任何市场界面就能把自己的插件跑起来；
4. **manifest 参考**：每个字段、每条正则、每个上限、权限全表（含"`net.credentials` 是第二道闸"
   这类必须讲清的关系）、`config` 的五种控件与 `secret` 的真实语义；
5. **桥接协议**：消息总表 + `init.surface` 的四种形状 + 六条铁律；
6. **34 个能力方法**逐项：payload、返回、错误、大小上限、以及"为什么这样设计"里**影响调用方**的
   那部分（例如 `truncated`、`at`、`targetExists`、`state` 的四个值）；
7. **事件**：只剩两个，其中一个**没有任何发射者**——直说，并指向番茄钟真正的发布方式；
8. **界面与几何**：矩形是声明的、`anchor`/`maxH`/`surface.blocks`、主题的两个通道、
   CSS 的四条纪律（`box-shadow`/`filter`/`transform`/`color-scheme`）；
9. **两个宿主的差异表**，以及 `workshop` 下该怎么降级；
10. **安全边界**（拿不到什么）、**发布**（zip 形状、`index.json`、版本与更新规则）；
11. **自检清单** + **常见故障对照** + **方法总表**。

配套一个 **可执行的自检工具**（`docs/plugin-testkit/`）：插件作者把它拷进自己的仓就能检查
manifest / 包 / 静态规则 / 协议行为，不需要本仓库、也不需要宿主代码。规范与工具分开写：
手册说"应该怎样"，工具检查"是否真的这样"。

## 明确不做

- **不复述宿主的实现细节**（为什么这样设计、内部类型、测试名）。读者不需要，而且会腐坏。
- **不放进 README**：README 是"用户能看到的行为"，一份 1000 行的开发者手册会把它淹掉；
  README 的「自己写一个插件」加一个指路链接。
- **不复制进 `market/` 仓**：那是一个独立仓，同一份契约放两处必然分叉；`market/README.md`
  继续讲"这六个插件各自怎么工作"。
- **不留"已退休接口"清单**：第一版写了，用户当场指出它除了误导没有用（混了四类东西，
  其中两条其实是**还在用**的），已整节删除。
- **不做"像素级"检查**：工具跑在 jsdom 里，没有排版、没有合成，几何与配色只能靠真机门禁。

## 影响的不变量

| 不变量 | 这次的关系 |
| --- | --- |
| `AGENTS.md §3.1` 权限表 | 文档第 4.1 节与工具里的 `PERMISSIONS` 是那 13 项的**对外副本**。`§3.3` 已加一句：改权限/方法/上限要同时改手册与工具的表 |
| `§3.3` 帧与能力边界 | 文档第 9 节是"两个宿主各服务什么"的对外说法；`AGENTS.md` 加了"契约只有一份"的指向 |
| `§3.5` 名字从 payload 来 | 文档把"名字是扁平名、键是相对路径、宿主从不接受 payload 里的路径"写成规则 |
| 内置 sample 与市场一致 | 不涉及 |
| `.dev/check-frontend.cjs` | 不涉及（没有新增宿主代码路径）；但工具会被拿去跑那六个官方插件，等于给它们加了一道外部体检 |

## 验证计划

- **示例插件逐字跑过**：用 jsdom（借 `market/node_modules`）把文档第 2 节的三个文件原样抽出来，
  按宿主协议驱动：`ready` → `init` → `storage.get` 回填 → 点按钮发 `bubble.say` → `storage.set`
  写回 → 收到 `theme` 换肤 → 未授权时按钮禁用 → 拒绝时显示宿主原文。**10/10 通过**。
- **自检工具在六个官方插件上跑**：`market/plugins/*` 全绿（或仅剩可解释的 WARN）；再用一个
  **故意写坏的夹具**证明每条检查真的会红（坏 id、未声明的 `netHosts`、缺 entry、用了
  `localStorage`、CSS 里有 `box-shadow`、调了不存在的方法、没申请的权限、未授权时仍发请求）。
- **事实逐条核对**：文档里的每个数字与正则都取自实现；写作与做工具的过程中改对了三处
  （子进程上限 32 不是 16；`surface.blocks` 是 500 毫秒节流；方法数是 34 不是 30）。
- `node .dev/check-frontend.cjs` 仍全绿。
