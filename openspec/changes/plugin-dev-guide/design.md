# design: 一份自包含的插件开发手册 + 一个可执行的自检工具

## 1. 三个决定

| 决定 | 备选 | 为什么 |
| --- | --- | --- |
| **一份文件、自包含** | 拆成"快速开始 / 能力参考 / 几何 / 发布"四份 | 读者的入口是"给你一份文档，去写插件"。多份文件会让人（和模型）只读到其中一份：协议在 A、上限在 B、几何在 C——而这三样正是最容易写错的地方 |
| **不引用宿主源码路径作为前提** | 让读者"需要时去看 `app_plugins.go`" | 用户的原话是"不需要获取宠物本地代码"。任何"详见 X 文件"都是把任务的一部分留在仓库里。引用只出现在"为什么这样设计"的附注里，且不承担契约功能 |
| **示例必须逐字可跑** | 只给片段 | 片段能读懂、拼不起来。桥接的坑全在**顺序**上（监听器先装再 `ready`、`init` 之前不发请求、`id` 对不上就丢弃），这些只有一整段能跑的代码才表达得出来 |
| **规范之外再给一个工具** | 只写规范 | 规范说"应该怎样"，工具检查"是否真的这样"。没有工具的规范等于让人自己当编译器；而"不用本地就能检查"正是用户的第二个要求 |

## 2. 结构：为什么是这 15 节（0–15）

读者的阅读顺序不是"概念→API"，而是"先跑起来，再按需查表"。所以：

```
0  摘要（60 秒）
1  运行模型          ← 只讲决定设计的那些事实（4 种挂载、互不共享内存、至少要有一个落点）
2  最小插件          ← 全文四文件，可直接粘贴
3  本地开发与手工安装 ← 没有市场界面也能跑起来
4  manifest 参考     ← 字段表 + 权限全表 + config/secret 语义
5  桥接协议          ← 消息表 + init.surface 四种形状 + 六条铁律
6  能力参考（按权限分组，34 个方法）
7  事件              ← 只有两个，其中一个没有发射者，直说
8  界面与几何        ← 矩形是声明的；anchor/maxH/blocks；主题两通道；CSS 四条纪律
9  两个宿主的差异     ← 谁服务什么，workshop 里怎么降级
10 你拿不到的东西     ← 安全边界（读者最容易在这里猜）
11 发布              ← zip 形状、index.json、版本与更新
12 自检清单          ← 勾选式，覆盖协议/能力/界面/包（并指向自检工具）
13 常见故障对照       ← 症状 → 原因（写错时最先需要的一页）
14 边界（该不该由插件做）
15 附录：方法总表
```

**故障对照表是这份文档最有价值的一节**，因为它不能从 API 列表推出来：一个读者照着 API 写，
仍然会把 `init` 丢掉、仍然会把浮层面的矩形当成 CSS 自动高度。

**没有"已退休接口"这一节，而且这是刻意的。** 第一版写了，用户当场指出它除了误导没有用——
拆开看，那张表混了四类东西：真被删掉的方法（`todos.*`、`timer.*`）、**其实还在用**的字段
（`panel`）、行为变更（`llm.chat` 的上下文）、以及数字变更史（17/15 → 13）。更糟的是对
这份文档的目标读者（只读这一份、没有旧资料的人或模型）：死名字进了上下文，就可能被当成
真 API 记住。所以处置是**删干净**，把还有用的部分搬到它该在的地方——"这张表就是全部"
写进第 4.1 节的注里，`panel`/`panelSlot`/`rectIndex` 本来就在字段表与第 5.2 节说清了。

## 3. 自检工具：为什么是"一个文件 + 一个 README"

```
docs/plugin-testkit/
├── README.md          ← 规范：查什么、怎么跑、怎么加自己的场景、查不到什么
└── plugin-check.mjs   ← 工具：一个文件，Node ≥18，零必需依赖（jsdom 可选）
```

- **一个文件**：读者把它拷到自己的插件仓里就能跑。多文件就要谈"目录结构"和"相对 import"，
  而这两件事恰好是他自己的仓说了算。
- **零必需依赖**：manifest / 包 / 静态规则这三组检查只用 `node:fs`/`node:path`。
  协议那一组需要 DOM，于是按需加载 `jsdom`（先看插件自己的 `node_modules`，再看调用方 cwd）；
  加载不到就**明确 SKIP 并说原因**，绝不假装通过。
- **规范与工具分离**：README 讲"为什么这条要查"（例如"未授权时不该发请求"为什么是硬规则），
  工具只输出 PASS/WARN/FAIL + 位置。两者的职责不同，放一起会让工具变成第二份手册。

### 3.1 四组检查

| 组 | 查什么 | 能不能在没有宿主的情况下查 |
| --- | --- | --- |
| manifest | 每一条校验规则（正则、上限、配对关系、`select` 约束、`background` 与权限的配对、`shareRead` 的形状、至少一个界面落点） | ✅ 纯 JSON 规则 |
| package | `entry` 存在、`assets` 都真的在包里、entry 里引用到的本地 `src`/`href` 存在 | ✅ 只看文件 |
| source | 调用的方法都在契约表里；每个方法需要的权限都已声明；不碰 `localStorage`/`document.cookie`/`fetch`/`XHR`/`new WebSocket`；CSS 没有 `box-shadow`/`filter`/`transform`、`:root` 透明且 `color-scheme: only light` | ✅ 静态读文本 |
| protocol | 真的把文档跑起来：发出 `ready`（`v:1`）、收到 `init` 不崩、每个 `request` 的 `id` 唯一且方法已知、拒绝一切时不崩、**未授权时不发那个请求**、收到未知消息类型不崩 | ⚠️ 需要 DOM（jsdom） |

### 3.2 协议那一组怎么在没有宿主的情况下跑

工具自带一个**假宿主**，形状照抄真实宿主：

- 收集插件 `postMessage` 出来的消息，校验 `{v:1,type,id}`；
- 按 `ready` 回一条 `init`（`permissions`/`granted`/`surface` 由工具按 manifest 生成，
  并跑三种挂载：`panel`+`workshop`、`surface#0`、`background`）；
- 对每个 `request` 回 `response`，并且**跑两遍**：一遍全部 `ok:true`、一遍全部 `ok:false`。
  后者是这个工具最有价值的一条——它逼出"宿主拒绝时插件会不会崩"；
- 再发 `theme` / `surface` / 未知 `type` / `v:2` 四种消息，确认插件忽略而不是抛错。

**没有真排版**：jsdom 不做布局，所以"内容会不会溢出声明的矩形"查不到——这是 SKIP 项，
README 里写明"几何要看真机"。

### 3.3 为什么工具不"顺手"读取宿主仓库

工具必须能在**只有插件源码**的地方跑。所以它的方法表、权限表、上限都是**内联常量**，
与手册第 4.1/6 节、宿主代码的三份副本，靠 `AGENTS.md §3.3` 的约定同步。
代价是可能落后；对冲手段是"拿六个官方插件当语料跑一遍"——它们是真实宿主的用户，
工具与宿主不一致时会立刻显形（`command-not-in-contract` 或"权限没申请"）。

## 4. 与 README / `docs/plugin-market.md` / `market/README.md` 的分工

| 文件 | 读者 | 讲什么 |
| --- | --- | --- |
| `docs/plugin-dev.md` | 插件作者（不一定是本仓库的人） | 契约：怎么写、怎么跑、怎么发 |
| `docs/plugin-testkit/` | 同上 | 怎么在本地把契约检查一遍 |
| `README.md` | 用户 | 「自己写一个插件」四步 + 指路链接 |
| `docs/plugin-market.md` | 维护者 | 控制中心这个程序自己的设计史与取舍 |
| `market/README.md` | 维护者 + 插件作者 | 那六个官方插件各自怎么工作 |

同一条规则只写一处，其余位置给链接。**能力/字段/上限**的权威副本是 `docs/plugin-dev.md`；
代码是它的实现。两者不一致时必须同一提交里一致。

## 5. 事实核对：这次写作中被改对的三处

1. **`process` 的子进程跟踪上限是 32**，不是 16（`maxTrackedChildren = 32`）。
2. **`surface.blocks` 是"最多每 500 毫秒生效一次"**，不是"一秒内合并"
   （`applySurfaceBlocksThrottled` 的 `minInterval = 500ms`）。
3. **方法数是 34**，不是 30（附录逐行数得 34；能力表也是 34）。这一处是写自检工具的表时
   发现的——工具必须逐条列全，一列就露出来了。

第二、三条正好说明为什么这份文档必须**逐条对代码抄**，而且**配一个能数数的工具**。

## 6. 没有为这份文档加静态门禁，以及为什么

一个自然的想法是加一条静态检查（"文档里提到的每个方法名都在能力表里"）。**没有加**：

- 能力表在 Go 里、手册在 markdown 里、工具在 JS 里，三者的"名字"可以合法地不同形，
  一个正则扫描会同时给出误报与假绿；
- 真正会腐坏的不是名字，而是**上限与语义**（`truncated`、`at`、`anchor`、`state` 的四个值）——
  那些连正则都提不出来。

所以守卫是三层：**协作约定**（`AGENTS.md §3.3`）+ **可跑的示例**（手册第 2 节）+
**可跑的工具**（`plugin-testkit`，拿六个官方插件当语料）。工具能被任何人复跑，所以它能发现
"手册过时了"——比一个会误报的门更有用。
