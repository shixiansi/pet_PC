# design.md — plugin-capability-versions

## D1 为什么是「版本下限」，不是「返回形状」

返回形状（每个方法一份 JSON Schema）听起来更彻底，代价却是把宿主变成每次回答的校验者：
多一个字段就破、少一个字段就破，而插件之间的协议本来就是作者自己商量的。版本下限只要求
一件事——「这个方法从 1.2.3 起是我认识的那个形状」——它是作者**能守住**的承诺，也是安装
对话框能念出来的一句话。

## D2 为什么在调用那一刻校验，不在安装时

两个理由：

1. **对方可能还没装。** 插件必须能先装后补依赖（今天的 36 个插件里就有一半依赖别人）。
   安装期校验会让"装一个还没装依赖的插件"变成不可能。
2. **对方可能被降级或换掉。** 每次调用都看当前版本，是唯一不会说旧话的检查。

代价是调用方在运行期才知道——但错误信息里有两个版本号，而 `plugins.services` 让它能在
调用**之前**就问清楚。

## D3 为什么下限是可选的

强制写会让作者抄一个没核对过的数字（"反正要写"），而那个数字比不写更糟：它看起来像承诺。
不写就是「我不在乎版本」，这是最常见的真实情况。

## D4 为什么复用 version.go 的 CompareVersions

`version.go` 已经回答过「磁盘上那份是不是落后于目录」，并且明确了预发布后缀的方向
（`1.2.0-beta.1` 与 `1.2.0` 相等）。再写一份「哪个版本更新」就是让下限和更新检查在某个
边界上互相矛盾——而那正是最难查的一类 bug。

## D5 检查顺序仍然是硬契约

`call.go` 的六步顺序（目标合法 → 不是自己 → 方法名合法 → payload 上限 → 调用方声明 →
目标启用/有权/声明了服务）保持不变；版本下限插在**第 5 步之后**，因为它读的是调用方声明的
那一项，而前五步都是"读，不改"。注释里的顺序表也同步更新了。
