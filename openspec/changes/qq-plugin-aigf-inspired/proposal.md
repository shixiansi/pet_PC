# proposal.md — qq-plugin-aigf-inspired（方案，待拍板）

> 一句话：参考 [nonebot-plugin-aigf-master](https://github.com/Funny1Potato/nonebot-plugin-aigf-master)
> 的"LLM 一次调用干完回复+记忆+表情包"的做法，把我们的 QQ 插件从"被叫才答的问答机"
> 改成"有记忆、有状态、会挑表情包的群友"——**但只在平台允许的范围内**。

## 1. 参考项目有什么（逐条对照我们能不能做）

| aigf 的能力 | 它的做法 | 我们能不能做 | 结论 |
| --- | --- | --- | --- |
| 一次调用完成 回复+记忆+表情包+命令学习 | `response_format=json_object` 强制 JSON | **不能强制 JSON**（宿主 `llm.chat` 没有 `response_format`/tools） | 改成"正文 + 尾部 JSON 围栏 + 旧标记兜底" |
| 四层记忆（短/长/群友/文化） | `memory/<群>/short_term.json`、`long_term.json`、`friends/<QQ>.json`、`culture.json`，LLM 自增删改 | 能做（storage 存 JSON） | 做 群记忆 + 群友卡片；"文化记忆"并入群记忆 |
| 社交能量 | 0~1 的数，回充/消耗，影响回复意愿 | 能做（一个数 + prompt 一句话） | 做，性价比最高 |
| 攒批（N 条 / T 秒）+ 不完整消息检测 | 攒够再处理，纯 @/连发延长等待 | 能做（ws 事件在手） | 可选，见 P3（成本↑↑） |
| 消息合并（同一人连发） | merge window 内合并 | 能做（需要等一小会儿） | 跟 P3 一起做 |
| 表情包：目录交给模型挑 id | `memes.json` + `collected.json`，模型返回 `{"type":"meme","id":...}` | 能做（我们有 317 张 + 标签 + 描述） | 做，两级检索（见 P2） |
| 表情包：自动收藏群里的图 | 图片 → VLM 描述 → 缓存 → 模型决定收藏 | 能做**但受 1 MiB 上限**（见 §2.3） | 做，同时必须先放宽宿主上限 |
| 图片理解 vlm / llm 两模式 | 独立 VLM 或图片直接进 prompt | 我们已经有了（`visionModel` + `images`） | 扩展成"整批图片"，不重做 |
| 联网搜索（tavily/bocha/bing/deepseek） | function calling 或两段式 | 能做（`net.fetch` + 域名白名单 + key） | 可选 P4 |
| 群系统通知（戳一戳/禁言/进群/撤回） | `[系统]` 进上下文 | 取决于协议端上报（我们只处理 `message_receive`） | 能做就做，小件 |
| 18 种消息段解析 | 卡片/合并转发/语音/位置… | 我们只渲染了 7 种 | 做，小件 |
| 跨插件感知 / LLM 调用别的插件 / 命令学习 / 跨 bot | `api_hooks`、合成群事件、peer HTTP | **做不到**：宿主没有这些钩子（只有 `share.*` 托盘） | 不做 |
| 二次元角色识别 / AI 生图 | 外部服务或 API | 需要额外服务与白名单 | 不做（要做也是独立变更） |

## 2. 先摆清平台的硬边界（决定方案长什么样）

`llm.chat` 一次能给的东西是固定的（`app_plugins.go`）：

| 参数 | 上限 | 对我们的含义 |
| --- | --- | --- |
| `system` | 4000 字符 | persona + 记忆 + 表情包候选 + 规则**全都要挤进 4000** |
| `text` | 4000 字符 | 攒批的新消息放这里 |
| `history` | 32 条 | 近期对话 |
| `images` | 4 张 | 一次最多看 4 张图 |
| 无 `response_format` / 无 tools | — | 只能靠 prompt + 稳健解析 |
| `net.fetch` | **单次 1 MiB**、30 s、域名白名单 | 大表情包会被截断（见 2.3） |

**2.3 顺手发现的一个真 bug**：真机 317 张表情包里，**156 张正好 1,398,104 字节 = 1 MiB 的 base64**，
也就是被 `net.fetch` 的 `LimitReader(1<<20)` 截断了。现在它们能显示（GIF 前几帧），但都是残图。
要收藏/导入更大的表情包，必须放宽这个上限（宿主改动 + 重新编译，成本很低）。

## 3. 分三期，每期都能单独上线

### P1 记忆与"人味"（不加新能力，成本只涨 20~50%）

1. **尾部结构化指令**（替代现在的 `〔表情:分类〕`）：正文照旧直接发到群里，后面跟一个
   ```` ```json ```` 围栏，字段 `{meme, remember[], forget[], friend{}, energy, silent}`。
   解析规则：只认**最后一个**围栏、解析失败就当作没有、正文里不出现围栏；
   旧标记 `〔表情:x〕` 仍然认（兼容老行为）。没有 `response_format`，所以这是"能稳定解析"的
   最优形状，而**群里看到的永远只有正文**。
2. **群记忆**：`memory/<群号>/notes`，LLM 自己增删改，≤20 条、每条 ≤60 字、带 `at`。
   每次调用把这份清单塞进 system（≤600 字符）。
3. **群友卡片**：`memory/friends/<QQ号>`，字段 `{nickname, aliases[], info, lastSeenAt, groups[]}`。
   system 里只放**当前这批消息里出现的人**（≤6 人 × 2 行），不塞全群。
4. **社交能量**：`state/energy/<群号>`，0~1，每条消息按"向基线回归 + 随机漂移"回充，
   回复后按字数消耗；system 里写一句"你现在的状态：精力充沛/有点懒/不想说话"。
   低能量时允许它对 @ 也只回一个"嗯"。
5. **可以沉默**：`{"silent": true}` 或只在正文里输出 `〔沉默〕` ⇒ 不发消息、只更新记忆/能量。
   这样"偶尔不想说话"不需要攒批就能实现。
6. **小件**：消息段渲染补齐（卡片/合并转发/位置/语音/文件/骰子…）、协议端若上报
   戳一戳/禁言/进群/撤回就渲染成 `[系统]`、回复时把文本里的 `@昵称` 转成真正的 QQ `@`、
   群内管理命令（`#状态` 看能量与记忆条数、`#忘掉` 清本群记忆）。

### P2 表情包：从"随机挑一张"到"模型挑这一张"

7. **两级检索**：群里模型先给"情绪/场景"（沿用现有的 10 个标签，或自由词），我们按标签+关键词
   过滤出 ≤12 个候选（id + 12 字描述），再让它返回 id。**317 张全塞进 prompt ≈ 4K token/次，
   两级只需 ~300 token**。选中后按 id 取字节发出去（`base64://` 不变）。
8. **自动收藏**：群里出现图片/表情包 → 先查 md5 缓存 `media/stickers/cache/<md5>`（命中即免单）
   → 否则 VLM 描述（标签 + 一句话）→ 把"候选"列进 system → 模型用 `{save_meme: <md5>}` 决定收藏
   → 收藏进 `media/stickers/`（复用现有导入管线）。上限沿用 `stickerMaxCount`，超出按
   "保存旧 + 使用少"淘汰（aigf 的归一化加权，比现在的 FIFO 好）。
9. **修 1 MiB 截断**：宿主把 `net.fetch` 的上限从 1 MiB 提到 8 MiB（`app_plugins.go`），
   重新编译两个程序；顺带把已截断的 156 张标注出来（`truncated: true`），工坊里可"重新下载"
   ——这些图片的原始 URL 早过期了，实际做法是让用户重新导入一次，导入时按 hash 覆盖。

### P3 群聊节奏（可选，成本最高，行为变化最大）

10. **攒批 + 未完成消息检测**：新增 `triggerMode: mention | batch`；batch 下攒够
    `batchCount`（默认 10）条或 `batchTimeout`（默认 30 s）后触发一次，纯 @ 或同一人连发则延长到
    `incompleteTimeout`（默认 40 s）；同一人 merge window（默认 5 s）内连发合并成一条。
    模型在 prompt 里看到"最近 20 条 + 本批新消息"，自己决定说不说话（`silent`）。
11. **整批图片理解**：本批里的图片都进 system（≤4 张/批），md5 缓存描述；解析未完成时整批
    推迟（aigf 的做法），超时则用 `[图片解析中]` 占位。

### P4 可选

12. **联网搜索**：`searchProvider: bocha | deepseek | bing` + key + manifest 加域名；
    两段式（先问"要不要搜"，再带搜索结果回答）——多一次调用，只在被问到时用。

## 4. 明确不做

- **跨插件感知 / LLM 调用其它插件 / 命令学习 / 跨 bot**：宿主没有这类钩子（`plugins` 能力表里
  没有 hook，也没有"投递合成消息"的入口）。要做先得改宿主，那是另一个变更。
- **强制 JSON / function calling**：没有 `response_format`、没有 tools。
- **"文化记忆"单开一层**：本质是 notes 的一个分类，多一层只会多一次读写。
- **AnimeTrace / AI 生图**：需要外部服务 + 白名单，收益/成本不匹配。

## 5. 落到位之后的目录（沿用 1.11 的布局）

```
memory/<群号>/notes            LLM 维护的群记忆（≤20 条）
memory/friends/<QQ号>          群友卡片
state/energy/<群号>            社交能量
media/stickers/index            表情包索引（新增 keywords/usageCount/truncated 字段）
media/stickers/catalog          由 index 派生的检索表（标签 → id 列表）
media/stickers/cache/<md5>      待收藏图片的 VLM 描述缓存（有上限，最旧淘汰）
history/<群号>                  近期往来（不变）
```

## 6. 需要拍板的四件事

1. **触发方式**：只保持"被叫才答"（最省）／加"可以沉默"（省，推荐）／攒批自主插话（最像 aigf，最贵）。
2. **记忆深度**：只有群记忆／群记忆 + 群友卡片（推荐）／再加独立"文化记忆"。
3. **表情包**：只做"模型挑 id"／再加"自动收藏群图"／并修 1 MiB 截断（需宿主改+重编译）。
4. **联网搜索**：不做／做（需要你给搜索 API 的 key 和域名）。
