# design: 日志系统

## 1. 三个决定，先摆出来

| 决定 | 备选 | 为什么 |
| --- | --- | --- |
| **等级 + 一直在写** | 保持"环境变量开了才有日志" | 报错时用户不会为了报错重新启动一次程序。默认 INFO 已经覆盖"谁调了什么、结果如何"，DEBUG 是排查时才开的细节 |
| **每个程序一个文件，读时归并** | 一个共享的 `app.log` | 两个进程往同一文件追加，轮转就是 rename 一个对方还开着的文件；而用户要的"一份日志"是**按时间排的视图**，那是读者的职责 |
| **写成一行五段的纯文本** | JSONL / 制表符 / 定宽列 | 用户第一件事是拿记事本打开它。JSONL 一屏能看 3 行；制表符会被编辑器折叠成空格；定宽列让「按空格切」变成不可能，而切分是读者唯一要做的事 |

## 2. 格式

```
2026-10-28T14:32:00.123+08:00 INFO plugin com.shixiansi.plugin-chat llm.chat ok（payload 84 B → 196 B，in 812ms）
```

`SplitN(line, " ", 5)` 就是全部解析。四条约束由写者保证：

1. **时间带偏移**（`TimeLayout = "2006-01-02T15:04:05.000Z07:00"`）。「09:05 提醒响了」离开时区
   没有意义，而让读文件那台机器去猜时区就是「默认一切都是 UTC」的另一半。
2. **插件列写 `-`** 而不是空。位置固定，跳过一列会让后面所有字段整体错位。
3. **正文压成一行**（`\r\n`/`\n`/`\r` → `" / "`）。一条能带换行的消息可以让**别人**伪造出
   一行看起来像宿主写的日志；`TestNewlinesInAMessageCannotForgeAnEntry` 守着。
4. **正文上限 4000 字节**，按 rune 截断并注明。一行日志不该把页面排版撑爆。

`ParseLine` 对读不出来的行**返回 false 而不是猜**：手改过的文件、断电后最后半行、以及被人
粘进来的别的东西都必须能活下来，而"丢掉那一行"是唯一能活的答案。

## 3. 轮转：不在两行之间持有文件

单文件 2 MB，超过就把 `x.log` 改名为 `x.log.1` 再重开；只有一代。

**每次写都是 open → append → close**，而不是"进程活多久就开多久"。这一条是被测试撞出来的
（`Market` 的每个用例都在 `TempDir` 清理时失败，报"文件正被另一个进程使用"），三个理由都
独立成立：

1. Windows 上**改名一个被打开的文件会失败**，于是轮转静默退化成 `Truncate`——「保留上一代」
   这个承诺变成假的，而页面上仍然显示两个文件；
2. 控制中心（另一个进程）要读它，用户也可能在记事本里打开它。一个常开的写句柄让两者都失败；
3. 退出时没有东西要 flush，硬杀不会留下半行。

代价是每行一次 open/close，按这个程序的日志量（最坏每秒几行）可以忽略。

## 4. 什么绝不允许进日志

对话正文、待办内容、插件设置的值、密钥。

记的是**形状**：方法名、插件 id、字节数、条数、tokens、耗时、错误文案。理由不是洁癖——
日志是给 issue 贴的，控制中心「高级 → 生成诊断报告」直接复制它；一处
`log.Debug("llm", payload)` 就能让每一份报告都不能外发。

三个地方各守一遍（三个不同的边界，漏一个都不行）：

- `internal/llm/log_test.go`：传输层不打印 messages、密钥、服务端返回体；
- `app_log_test.go`：闸门与 `llm.chat` 不打印 payload 与回复正文；
- `tools/plugin-market/logapi_test.go`：页面读到的就是文件里真有的。

`llm.Settings.String()` 从它被写出来那天起就是 `key=set`，这次没有例外。

## 5. 桌宠那边记什么

| 位置 | 行 |
| --- | --- |
| `PluginRequest`（**唯一**闸门） | 一次调用一行：成功 INFO / 拒绝或失败 WARN，带方法、payload 字节、返回字节、耗时、错误原文 |
| `llm.chat` | 请求（端点/模型/消息数/历史轮数/工具名/图片数，DEBUG）、每轮（耗时/尝试次数/字数/tokens/finish/工具调用数，尝试>1 时升 WARN）、完成（INFO）、失败（WARN + kind）；预算拒绝 WARN |
| `runPluginTool` | 每个工具调用一行（名字、成功与否、参数字节、返回字节） |
| `internal/llm` | POST 端点/模型/条数、HTTP 状态、`stream_options` 自愈、重试与等待、流摘要（帧数、字数、tokens）、非流式回退 —— 全部 DEBUG |
| 子系统 | 托盘、窗口与裁剪、快捷键、提醒、设置热重载、插件迁移、控制中心启动；失败一律 WARN/ERROR |
| 页面 | `App.PageLog(level, msg)`：`fail()` 里与 toast 同一句（ERROR），`debug()` 走 `DebugLog`（DEBUG） |

**为什么成功也记 INFO**：一份只有错误的日志回答不了"它到底有没有被调用"——那是「点了没反应」
最需要的第一条信息。量大吗？一个每 2 秒轮询 `process.state` 的插件一天约 4 万行 ≈ 一个 2 MB
文件，正好一次轮转。要安静就 `PETPC_LOG_LEVEL=warn`。

**为什么闸门拒绝是 WARN 而不是 ERROR**：拒绝是闸门在工作（权限没授、插件被停用），用户能修；
ERROR 留给"用户会看见的失败"。两者的区别写进了 README 的等级表。

## 6. 控制中心那边

- `Market.LogTail(q)` 读两个文件（含 `.1`），按时间归并，**新在前**：轮询每 2 秒带来三行新记录
  时，用户正在读的那一行不该动。
- 返回 `{entries, files, scopes, dir, note}`。`note` 解释空结果——「还没跑过」「筛选没匹配」
  「读不出来」是三种完全不同的状态，一块空白一个都答不了（和 `diagnostics.go` 给缺失文件也
  打一行是同一个理由）。
- 页面的筛选**在 Go 侧**做（`logging.Query`），而不是把 500 行发给页面再筛：等级与子系统是
  读的时候就知道的信息，把它们变成前端的字符串比较等于同一个规则两份实现。
- 自动刷新 2 秒、可关；关掉时定时器整个停，不在回调里判断。
- 复制走 `ClipboardSetText`（与高级页同一条路），并把"这个环境没有剪贴板"照实说出来。
- 页面不提供"清空"：写文件的是另一个进程，删除/截断一个正在被追加的文件只会得到稀疏文件与
  一段消失的历史；保留策略交给轮转。

## 7. 读的一侧为什么不能读缓存

`LogTail` 每次真的读文件。看起来浪费，但：桌宠随时可能轮转；用户在记事本里删了文件；
两个程序的启动顺序不定。一个缓存要么需要一份跨进程失效协议（新的失败模式），要么给出一个
比文件更旧的答案（"日志里没有"是最气人的那种错误）。500 行 × 2 文件解析一遍在这个尺度上
是免费的。

`readFile` 只读每个文件最后 512 KB：轮转后的文件可能有 2 MB，而 2 秒一次把 2 MB 解析一遍
会让这一页和桌宠抢磁盘。

## 8. 与旧 `debug.log` 的关系

不再写、不再读。它是"有开关才有日志"的化身，留着无妨（用户的数据目录里可能还有一份），
但任何代码路径都不再引用它——`.dev/check-frontend.cjs` 有一条检查盯着"`PETPC_DEBUG` 的门
不许回来"。

## 9. 已知的取舍

- **`INFO` 会比以前吵**。这是有意的：以前那些行只在你设了环境变量时才存在，所以"吵"的那一半
  从来没被看见。`PETPC_LOG_LEVEL=warn` 是给"只想看失败"的人的。
- **两个 `logLevelFromEnv` 各写一遍**（宿主 / 控制中心）。两个程序没有共享的"这个安装怎么配置"
  的家，为一个四行函数建第三个文件不划算；变量名写进 README，用户只需要设一次（两个程序都读）。
- **没有跨进程的实时推送**。2 秒轮询在"一边操作一边看"的用法下看不出延迟，而事件推送要么
  需要再一个进程间通道，要么让页面在桌宠退出后永远停在最后一行。
