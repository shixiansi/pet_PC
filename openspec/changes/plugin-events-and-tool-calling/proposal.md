# proposal: 事件带上时间，并让模型有手可动

## 现状（已实读代码确认）

宿主与模型之间目前只有一条路：插件调 `llm.chat`，宿主把消息发出去，把文字流回来。
除此之外**没有任何通路**把"模型决定要做一件事"变成"宿主真的做了它"。

- `internal/llm/protocol.go` 的 `ChatRequest` 只有 `model/messages/stream/temperature/max_tokens`，
  没有 `tools`；流式解析（`ParseFrame`）不认 `tool_calls`。
- 宿主自己的能力（待办、番茄钟、提醒、气泡）全部挂在 `App` 上，只对**前端**开放
  （Wails 绑定）和**插件**开放（`PluginRequest` + 权限闸门），对模型不可见。
- 事件已经在投递（`SubscribableEvents` 四个名字，其中两个是边缘事件），
  但信封 `PluginEventView{PluginID, Name, Payload}` **没有时间戳**。

所以在"效率桌宠"这个定位下，模型是个只能说话的顾问：它看得见你今天的待办（宿主把
快照拼进 prompt），却没法替你完成一条。

## 两件事，顺序不能反

**一、事件信封带本地时间。** 事件流是插件拿去给模型看的东西，而送达顺序回答不了
"什么时候"——一帧卡了两分钟才送到，描述的仍是它发生的那一刻。没有时间戳，接收方只能
拿自己的钟去盖，于是"14:32 结束的专注"变成"我 14:34 才发现它结束"。

**二、工具调用（本提案的主体）。** 让模型能调一组**宿主内置**的动作，执行前过同一道
权限闸门。

## 定位约束（决定了方案形状）

宿主不认识任何具体插件，也不自带对话界面（`app_chat_slot.go`）。所以：

- **不**做"宿主自持 Agent + 内置对话"——那是撤销一个已经做过的架构决定。
- 做法是：**大脑仍在插件，宿主多了一双手**。插件决定问什么、用哪个模型、要不要用工具；
  宿主决定某个工具能不能真的执行。

## 非目标

- Anthropic 原生 `/v1/messages` 与可替换的 provider 抽象（README 里那句"Provider 接口
  已留位"本来就不成立，见本仓 AGENTS.md §5）。
- 长期记忆文件（`PARTNER.md` 那类）。
- 宿主侧对话界面。
- 让插件自己执行工具（见 design 里"为什么工具必须是宿主内置"）。

## 验收

- 事件：`pet:plugin-event` 的每一帧都有 `at`，RFC 3339 + 本地偏移，且由**唯一**那个
  发射函数盖章（不是每个调用点自己盖）。
- 工具：模型能在一轮对话里连调两个工具并拿到结果，最终文本照旧流式返回；
  未授权的工具不会被调用、也不会被"静默跳过"——它根本不出现在模型看到的工具列表里。
